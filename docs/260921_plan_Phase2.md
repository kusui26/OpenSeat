## 1. Phase 2 のゴールと完了条件

### ゴール

**Phase 1 で作った純粋なドメインロジックに、永続化・API・画面・通知・運用を着せて、模擬フードコートで人に使ってもらえる状態にする。**

Phase 1 が終わった時点で、サーバも画面も無く、あるのは `packages/core` と比較レポートだけでした。Phase 2 が終わった時点では、**スマホで QR を読めば席の順番待ちができ、呼ばれたら座れ、退席を押せば次の人に渡る**ものが本番環境で動いています。

**Phase 2 のいちばん難しいところは、ロジックではなく量です。** 作る画面が 10.1 に 12 面あり、API が 9.7 に 13 本あり（表は 8 行だが、管理の 1 行が 4 本を含む）、そのうえで現場に出す準備（印刷・監視・手順書）が要ります。**順番を間違えると、どれも半端なまま Stage A の日が来ます。** 3 章はその順番の話です。

## 3. PR の粒度と順番をどう決めたか

ここが本書の中心です。分解の結果だけでなく、なぜその分解になったかを残します。

### 3.1 粒度の原則

Phase 1 の 6 つの原則はそのまま引き継ぎます。Phase 2 で変えるのは 1 つだけです。

**原則 1: 1 つの PR は、レビュアーが答えられる 1 つの問いに対応する。**（据え置き）

**原則 2: 実装は 400〜600 行を目安にする。テストは別枠で数える。**（Phase 1 の 300〜500 行から広げる）

画面のコードは行数が膨らみます。1 つのフォーム、1 つの状態表示、1 つの色分けが、それぞれ数十行になるためです。**行数を守ろうとして画面を半分だけ作る PR を出すのは本末転倒**なので、目安を広げ、**画面の PR は「1 つの面」または「1 つの一周」で区切る**ことにします。

**原則 3: `main` は常に緑で、意味のある状態に保つ。**（据え置き）

Phase 2 では「デプロイできる状態に保つ」も加わります。PR 9 以降、`main` は常に本番に出せる状態です。

**原則 4: 後で捨てる実装を書かない。**（据え置き。ただし 1 つだけ例外がある）

例外は `apps/spike` で、**これは最初から捨てる前提で書き、PR 1 で消します。** 例外を許したのは、それが「技術選定の関門」だったからです（9.13）。Phase 2 の中で同じことをしません。

**原則 5: 宣言 → 振る舞い → 検証 の順に進む。**（据え置き。3.2 の判断 1 に効く）

**原則 6: 検証の道具を早く立ち上げ、以降の PR を自動で叩かせる。**（据え置き。3.2 の判断 2 に効く）

### 3.2 順番を決めた 3 つの判断

#### 判断 1: CLAUDE.md 3.2 の「残る 3 つの DSL」を最初に宣言する

CLAUDE.md 3 章は、ファット・コントローラーを「気をつける」ことではなく **構造的に不可能にする**ことで防ぐ、としています。その仕掛けが 5 つの宣言（DSL）です。

| # | 宣言 | いつ |
|---|---|---|
| (1) | スキーマ DSL（Drizzle） | **Phase 2 — PR 1** |
| (2) | 遷移 DSL（状態機械） | Phase 1 ✅ |
| (3) | 不変条件 DSL | Phase 1 ✅ |
| (4) | 権限 DSL | **Phase 2 — PR 3** |
| (5) | API 契約 DSL（Zod） | **Phase 2 — PR 2** |

**保証は 5 つ揃って初めて成立します。** Phase 2 には画面と API の PR が 12 本あり、そのすべてがこの宣言の上に乗ります。**宣言の無いまま 12 本を進めると、判断がハンドラに散る**のはほぼ確実です。CLAUDE.md が挙げている判定基準はこうでした。

> **コントローラーとビューを何度書き換えても、データの整合性が壊れないこと。**

これを満たすには、書き換える対象より先に宣言がある必要があります。

**代替案**: 歩くスケルトン（受付から退席までの最小の一周）を先に作り、必要になった宣言を後から足す。

**却下の理由: それはもう終わっているからです。** Phase 1 の判断 1 は「この Phase には I/O が無く、歩くスケルトンが見つけるものが無い」を理由に宣言を先にしました。Phase 2 には I/O があるので、同じ論法は使えません。**しかし 1 日スパイクが、まさにその歩くスケルトンでした。** 宣言なしで一周を通し、そこで分かることは全部出ています。

- `packages/core` は ESM のまま素直に載る（変換も回避策も不要）
- `node:sqlite` は動く（ただし実験的）
- 落ちても入力を流し直せば状態が戻る
- **層の分け方（ハンドラ 4〜5 行、判断は core）が、その規模でも窮屈ではなかった**
- コンテナは 173MB で組み上がり、ボリュームに置いた記録は作り直しても残る

**二度やる必要はありません。** スパイクがあるからこそ、Phase 2 は宣言から始められます。

#### 判断 2: 本番に置くのを、全部できてからではなく「一周が通った直後」にする ← 本書で最も重要な判断

**PR 9 で Railway に置きます。** 19 本のうち 9 本目、段 B の最後です。以降の PR は毎回、実機のスマホと実際の回線で確かめます。

**代替案**: 段 E でまとめてデプロイする（作るものが全部できてから、置く）。

**却下の理由は 3 つあります。**

1. **「手元では動く」を早く潰せる。** 実機のスマホでの QR の読み取り、モバイル回線での再送、長い接続がプロキシ越しに保つか、iOS の Web Push。**どれも手元の Mac では分かりません。** 遅く置くほど、分かるのが遅くなります。
2. **12.4 が求める準備を、締切直前の作業にしない。** 実証実験の事前準備チェックリストには「本番環境のデプロイ、監視、バックアップ、`全席解放` の手順」が並んでいます。これを Stage A の直前にまとめてやると、**必ず何かが間に合いません。**
3. **9.13 が残した未知を早く測れる。** 再デプロイの停止時間、月額、長い接続の保持。**これらは運用時間帯を避ける判断（CLAUDE.md 8）と、コストの食い違い（9.1 の 1,500 円 vs 14.2 の 1,000 円）の解決に要ります。**

これは Phase 1 の判断 3（シミュレータを末尾ではなく中盤に置く）とまったく同じ構造です。**検証の環境を早く立て、以降の PR をそれで叩く。** そして同じ理由で重要です —— **日程が押したときに落ちるのが「検証の環境」になってはいけない。**

**この判断には代償があります。** PR 9 は Railway のアカウントとドメインという、人の手が要るものに依存します。**揃わなければ PR 9 で止まります**（2 章の「着手前に、人の手で用意するもの」）。それでも遅らせるより良いと判断しました。

#### 判断 3: Stage A を 2 回に分け、1 回目を早めに置く

12.2 は「自宅や YOXO BOX のイベントスペースで机 6 卓の模擬フードコートを作り、**友人 10 人で 2 回テストする**」と書いています。**2 回と書いてあるのを、素直に 2 つの PR にします。**

| | いつ | 何のため |
|---|---|---|
| **1 回目**（PR 17） | 面が揃った直後 | **見つけるため。** UI の迷い、ルールの穴、呼び出しの気づかれなさ。出た問題を直すところまでが PR 17 |
| **2 回目**（PR 19） | 修正のあと | **確かめるため。** 直したものが効いたか。11.1 の完了条件はここで閉じる |

**1 回目を「全部できてから」にしないことが要点です。** Stage A は試験ではなく発見の道具で、**早いほど直す時間が残ります。** Phase 1 でシミュレータを中盤に置いたのと同じ考え方です。

**代替案**: Stage A を 1 回だけ、Phase 2 の最後に置く。
**却下**: そこで UI の作り直しが必要だと分かったとき、直す時間がありません。12.3 が Stage A を「機能とルールの穴を潰す」段階と定義していることとも合いません。

### 3.3 分解の副産物として得られること

- **9.7 の API 表と、10.1 の画面表が、それぞれどの PR に対応するかが分かる**（4 章の 2 つの対応表）。仕様の表とコードが 1 対 1 であることを、Phase 1 と同じやり方で保てる
- **Stage A に必要な物理（印刷した QR、ボード、実機）が、いつ揃うかが日程として見える**（PR 13 で印刷、PR 11 でボード）
- 止める場所を選べる（4 章の「最短の打ち切り線」）

#### PR 1 — スキーマと永続化

> **問い: 9.6 のデータモデルは `core` の型と 1 対 1 か。整合性は DB の制約として表現されているか。落ちても状態を取り戻せるか。**

**出典**: 全体プラン 9.6、9.4、9.13 ／ **依存**: — ／ **見積**: 10h ／ **目安**: 実装 500 行

**実装**

1. **`apps/server` を作り、`apps/spike` を消す。** スパイクの `Dockerfile` は `APP` を差し替えるだけで使える
2. **Drizzle のスキーマ**（`apps/server/db/schema.ts`）。9.6 の表を 1 対 1 で写す。**ここが唯一の出典**で、マイグレーションは生成物とする（CLAUDE.md 3.2(1)）
3. **整合性を DB の制約として表す。** アプリ側のチェックは二重防御であって代替ではない

```ts
// 例: 1 つの席に有効なチケットは最大 1 枚（不変条件 one_ticket_per_table を DB でも縛る）
uniqueIndex('one_active_ticket_per_table')
  .on(tickets.tableId)
  .where(sql`state IN ('CALLED','SEATED')`)
```

4. **記録の 3 本立て**（下記の「この PR で決めること」）
5. 再起動の復元と、その結合テスト

**この PR で決めること（2 つの ADR）**

**(a) SQLite のドライバ（ADR-0012）**

| 案 | 利点 | 欠点 |
|---|---|---|
| `node:sqlite` | **依存ゼロ。** スパイクで動作確認済み | **実験的。** 毎回 `ExperimentalWarning` が出る。「いつ変わってもおかしくない」と公式が言う層に、実証実験の記録を置くことになる |
| `better-sqlite3` | 成熟。Drizzle のいちばん枯れた経路 | ネイティブ拡張。**Alpine（musl）で prebuilt が効かないと、組み立てに道具が要る**（イメージが膨らむ） |
| `libsql` | prebuilt あり、Drizzle 対応 | ベンダーが 1 つ増える |

**推奨は `better-sqlite3`。** 理由は「本番のログに実験的警告が出続けると、本物の問題が埋もれる」ことと、**実証実験の記録を実験的な API の上に置きたくない**ことです。ただし **3 つとも実際に組み立てて測ってから決めます**（イメージの大きさ、組み立て時間、`node:22-alpine` のままで済むか）。`better-sqlite3` が Alpine で組めないなら、`node:22-slim` にするか `node:sqlite` に戻します。

**(b) イベントログとスナップショットの形式（ADR-0013）**

**ここで Phase 1 からの申し送りを片づけます。** PR 14 で分かったことは、こうでした。

> **イベントログだけでは、席の稼働率を計算できない。** `TableReportedInUse` は「使用中（誰か不明）」と「使用中（本人）」の両方へ向かい、`StillHereAnswered` は席が確認要から使用中へ戻ったことを語らず、`VenueOpened` はどの席が運用に戻ったかを持たない。**イベントは「起きたこと」を語るが、「席がいまどの姿か」を語る責任を負っていない。**

**そして、9.4 の記述にも穴があります。**

> 9.4:「発生したイベントは同一トランザクションで SQLite に追記し、状態スナップショットを更新してから WebSocket に配信する。**起動時はスナップショット＋以降のイベントで復元。**」

**「以降のイベントで復元」は成り立ちません。** イベントから状態を組み直せないのは上と同じ理由です。**スナップショットが遅れた瞬間に、その遅れを埋める手段が無くなります。**

**推奨する形（3 本立て）**

| 記録 | 何のため | 書くタイミング |
|---|---|---|
| **スナップショット** | **復元のため。** `VenueState` をそのまま 1 行 | **状態が変わるたび、同じトランザクションで。遅れを作らない** |
| **イベントログ** | 配信・統計・監査のため。`DomainEvent` を追記 | 同じトランザクション |
| **席の状態の履歴**（投影） | **稼働率のため。** 席がどの姿に、いつからいつまでいたか | 状態が変わったとき、変わった席の分だけ |

- スナップショットは数 KB（席 30・チケット 200 で十分小さい）。更新は 1 分に数十件（9.1）なので、毎回書いても SQLite には軽い
- **3 本目は「投影」であって新しい真実ではない。** `VenueActor` は変更の前後の状態を両方知っているので、差分を書くだけです（シミュレータの `tableSpans` と同じ形）。**`core` のイベント契約には触りません**
- **9.4 の「以降のイベントで復元」は誤りなので、全体プランを直します**（CLAUDE.md 6.4）

> **実装で変わった点（2026-09-22）。** 1 本目の「スナップショットを 1 行」は採りませんでした。**`venues` ＋ `tables` ＋ `tickets` の行そのものを状態とします。**
>
> 理由は、**塊で持つと整合性を DB の制約として書けない**ことです。この PR の実装 3 が求める `one_ticket_per_table` の部分一意インデックスは、JSON の塊には張れません。塊と行の両方を持てば、制約は行という写しにしか効かず、どちらが正かという問いが残ります。9.6 がすでに `tables` と `tickets` を宣言している以上、二重に持つ理由がありません。
>
> 残りの 2 本（イベントログ、席の姿の履歴）は推奨のとおりです。詳しくは [ADR-0013](adr/0013-what-we-record.md)。

**テスト**

- **9.6 の表の各行が、スキーマに 1 対 1 で存在する**（対応表のテスト）
- **DB の制約が実際に効く**: 1 つの席に 2 枚の有効チケットを入れようとすると、書き込みが落ちる
- 落として起こし直すと、同じ状態に戻る（メモリ内 SQLite ではなくファイルで）
- `core` の `VenueState` を往復しても、値が 1 つも変わらない（丸め・型の欠落が無い）
- 席の状態の履歴が、開始から終了までを隙間なく覆う（Phase 1 の `spanCoverage` と同じ検算）

**完了条件**: 9.6 のスキーマが宣言され、制約が DB で効き、再起動で状態が戻り、ADR-0012 と 0013 が書かれている。`apps/spike` が消えている。

#### PR 4 — VenueActor（直列化・冪等キー・復元）

> **問い: コマンドが 1 件ずつ順に適用され、再送で二重適用されず、落ちても取り戻せるか。**

**出典**: 全体プラン 9.4 ／ **依存**: PR 1、PR 3 ／ **見積**: 10h ／ **目安**: 実装 400 行

**実装**

1. **施設ごとに 1 つのアクター。** コマンドを 1 件ずつ順に適用する。**並行に来たものはキューに積む**
2. **`tick` を 10 秒ごとに呼ぶ**（9.4）。個別のタイマーを持たない
3. **同じトランザクションで**: イベントを追記 → スナップショットを更新 → 席の状態の履歴を書く。**そのあとで配信する**
4. **冪等キー**（ADR-0015）。モバイル回線の再送で二重適用しない
5. **不変条件が破れたらロールバック**（9.12）。壊れた状態を書き込まない
6. 起動時に復元

**この PR で決めること（ADR-0015）: 冪等キーの設計**

| 決めること | 推奨 |
|---|---|
| 誰が作るか | **クライアント。** 画面がコマンドごとに UUID を作って送る |
| 何を鍵にするか | `(venue_id, idempotency_key)` の一意制約 |
| いつまで覚えるか | **24 時間。** 実証実験は 1 日単位で、それ以上の再送は別の操作とみなしてよい |

- 落として起こし直すと、同じ状態に戻る

**完了条件**: 直列化・冪等・復元の 3 つが結合テストで緑。ADR-0015 が書かれている。

#### PR 7 — リアルタイム配信

> **問い: 呼び出しから画面の更新まで数秒以内か（9.1）。接続が切れても戻るか。**

**出典**: 全体プラン 9.5、9.1 ／ **依存**: PR 6 ／ **見積**: 8h ／ **目安**: 実装 400 行

**実装**

1. **トピック 3 つ**（9.5）: `ticket:{id}`（本人）、`venue:{id}:public`（ボード・空き状況）、`venue:{id}:staff`
2. **フォールバックの階段**: WebSocket → SSE → 5 秒ポーリング
3. **再接続**（指数バックオフ）と、**再接続時の取りこぼし防止**（最後に受け取ったイベントの位置から追いつく）
4. **利用者ページの接続をハートビートとして扱う**（9.5、7.9 の放置判定）

**この PR で決めること（ADR-0014）: 配信方式**

スパイクで **SSE は Railway 越しでも保つか**を測っています（[報告](260921_report_spike.md) の 3.2）。その結果で決めます。

| 案 | 利点 | 欠点 |
|---|---|---|
| **WebSocket ＋ SSE フォールバック**（9.5 の既定） | 双方向。将来の用途に広い | 実装が 2 本になる。プロキシで切られることがある |
| SSE だけ | **1 本で済む。** スパイクで動作確認済み。プロキシに優しい | サーバ → クライアントの一方向（いまの用途には足りる） |

**推奨は「SSE を主、WebSocket は持たない」。** 理由は **いまの用途がすべて一方向だから**です。利用者の操作は HTTP の POST で足り、双方向が要る場面がありません。9.5 は WebSocket を既定としていますが、**9.2 は最初から SSE をフォールバックとして挙げており、方向性は矛盾しません。** 採る場合は全体プラン 9.5 を直します。

**テスト**

- 呼び出しから画面の更新まで **3 秒以内**（9.1 の「数秒以内」を検査可能にする）
- 接続を切って戻すと、取りこぼさずに追いつく
- WebSocket を塞いだ環境でポーリングに落ちる

**完了条件**: 3 つのトピックが配信され、切断から復帰でき、ADR-0014 が書かれている。

## 6. すべての PR に適用する横断ルール

各 PR の詳細には書きません。全部に効きます。

### 6.1 進め方

1. **ブランチを切る。** `feat/p2-NN-短い説明`（例 `feat/p2-04-venue-actor`）
2. **PR 本文に、対応する全体プランの節番号と「問い」を書く**
3. **`pnpm verify` と E2E（PR 8 以降）を通してから PR を出す。** 通っていないなら、通っていないと明示する
4. **PR 9 以降は、本番に置いて実機で確かめてから出す**
5. マージはマージコミット（squash しない）。`main` に直接 push しない

### 6.2 実装 — 層を越えない

**CLAUDE.md 3 章が本書のすべての PR に適用されます。** Phase 2 はハンドラと画面を大量に書くフェーズなので、**ここが崩れるとすべてが崩れます。**

- **ハンドラが書いてよいのは 5 行。** 入力の検証 → 実行者の特定 → コマンドの組み立て → `dispatch` → 整形。**`if (ticket.state === 'CALLED')` が現れたら設計の誤り**
- **ビューは業務判断をしない。** 期限の判定も権限の判定も画面に書かない
- **永続化層に業務判断を書かない。** 条件分岐による業務判断は `core` にある
- **ルートから `db/` や `drizzle` を直接 import しない**（`scripts/check-architecture.mjs` が検査する）
- **`packages/core` の純粋性を守る。** Phase 2 で `core` に足すのは権限表（PR 3）だけ。**時刻・乱数・I/O を持ち込まない**
- **新しいコマンドを足したら、権限表にも足す**（PR 3 以降）。忘れると誰も実行できないか、誰でも実行できてしまう

### 6.3 テスト

- **仕様の表は、1 行 1 テストで写す。** 9.6 のデータモデル、9.7 の API、10.1 の画面、7.8 の分岐
- **画面が出した操作は、必ず通る。** Phase 1 の PR 10 で見つかった欠陥（画面とコマンドが別の式を見ていた）を、サーバ越しでも防ぐ
- **時計を偽装して期限切れを再現する**（9.12）
- **実機で確かめるものは、自動テストにしない。** QR の読み取り、ボードの視認性、iOS の Web Push、印刷。**手で確かめたことを PR 本文に書く**
- テストの名前は日本語で、仕様の文言に寄せる

### 6.4 セキュリティ（CLAUDE.md 7）

**Phase 2 で初めて本物の秘密を扱います。** 全 PR に効きます。

- **収集しない**: 氏名・電話番号・位置情報・カメラ画像
- **ログに出さない**: チケットの秘密パラメータ、座席トークン、セッション、Web Push の購読情報、メールアドレス。**エラーの文脈情報にも含めない**
- **秘密は `.env` で扱い、コミットしない。** `.env.example` に鍵の名前だけ
- **スタッフ・管理者の全操作を監査ログに残す**
- **通知先はチケット終了時に削除する**

### 6.5 ドキュメント

- **設計上の判断をしたら ADR を書く**（9 章）
- **全体プランと食い違いを見つけたら、実装を進める前に全体プランを直す。** Phase 2 では既に 2 か所見つかっている（9.4 の「以降のイベントで復元」、9.5 の配信方式）
- **本書も更新する。** 見積もりが外れた、PR を分けた、順番を入れ替えた、はすべて記録に値する
- **各 PR に「実装後の記録」を書く。** Phase 1 のプランがそうなっている

## 7. 設計上の先決事項

実装を始める前に決めておくこと。迷いながら書くと後で揃わなくなります。

### 7.1 `packages/core` には、もう機能を足さない

Phase 2 で `core` に足すのは **権限表（PR 3）と `Actor` の拡張だけ**です。ほかは触りません。

**理由**: `core` は 1,623 本のテストと 17 個の不変条件で守られています。**そこに手を入れると、守りを一度崩すことになります。** サーバで必要になったものは、まずサーバ側で解けないかを考えます。

**例外の判断**: 「`core` の契約が足りない」と思ったときは、**本当にドメインの話か**を確かめます。PR 14 の稼働率の問題は、`core` のイベントに足すのではなく**サーバ側の投影**で解きました（PR 1）。同じ形で解けないかを先に考えます。

### 7.2 施設は最初から複数を想定する

9.13 の「守るべき原則」はこうでした。

> **施設ごとにプラットフォームのアカウントやプロジェクトを作らず、自分が所有する 1 つのマルチテナントなアプリを運用すること**

**実証実験は 1 施設ですが、最初から複数施設のつもりで作ります。** すべてのテーブルに `venue_id` を持たせ、すべての API が施設を受け取り、`VenueActor` は施設ごとに 1 つです。**後からマルチテナントにするのは、ほぼ作り直しになります。**

### 7.3 時刻はサーバだけを信頼する

`core` は UTC のミリ秒しか知りません（Phase 1 の 7.6）。Phase 2 では境界がこう振る舞います。

- **タイムゾーンの変換は境界で。** 施設のローカル時刻（既定 `Asia/Tokyo`）で運用スケジュールを評価し、`core` には絶対時刻を渡す
- **クライアントの時計を信じない。** 期限は絶対時刻で渡し、**サーバとの時計差も渡す**。カウントダウンは表示だけを担当する（9.4）
- **保存は UTC、表示は施設のタイムゾーン**（CLAUDE.md 6）

### 7.4 失敗は `Result`、文言は i18n

`core` は `Result<Decision, Rejection>` を返します（Phase 1 の 7.3）。Phase 2 は、

- `RejectionCode` → HTTP の状態コード の対応表を 1 か所に置く
- `RejectionCode` → 利用者向けの文言 の対応表を `packages/shared` に置く（PR 2）
- **ハンドラで文言を組み立てない**

### 7.5 画面は状態を描くだけ

**7.3 のチケットの状態機械が、そのまま画面の出し分けになります。** 状態ごとに何を出すかを表で持ち、画面はそれを引くだけにします。**条件分岐を画面に書くと、状態が増えたときに漏れます。**

同じことが座席 QR にも当てはまります。**`resolveTableScan` が返した結果を描くだけ**で、画面は分岐を持ちません（PR 10）。

### 7.6 実機で確かめるものを、最初に決めておく

自動テストにできないものがあります。**「あとで確かめる」にすると確かめません。**

| 確かめるもの | いつ | どうやって |
|---|---|---|
| QR が実機で読める | PR 13 | 刷って、iOS と Android で読む |
| ボードが 3m 離れて読める | PR 11 | タブレットを置いて離れる |
| Web Push が届く | PR 16 | iOS と Android の実機 |
| モバイル回線で使える | PR 9 以降 | Wi-Fi を切って操作する |
| 印刷の余白と光の反射 | PR 13 | 実際に卓に置く |

### 12.3 Phase 1 から引き継ぐ「効いた進め方」

Phase 1 で繰り返し効いたやり方を、Phase 2 でも使います。

1. **検査を足したら、わざと実装を壊して落ちることを確かめる。** Phase 1 では 3 度これで初めて穴が分かり、PR 14 では 9 つの変異のうち 1 つが捕まらなかった
2. **「同じ判断が何か所にあるか」を数える。** だいたい 1 か所が抜けている。抜けを見つけたら、直すより先に「宣言 1 つで全部を縛れないか」を考える
3. **数字が「それらしい」かではなく、理屈と合うかで見る。** PR 14 のノーショーの取りこぼしは、`4.3 件 × 7 分 ≒ 30 分` のはずが 10 分だったことで気づいた
4. **性質テストの生成器は、目的の状態に届いていないことがある。** Phase 2 では E2E が同じ性質を持つ。**通っていることと、踏んでいることは違う**
