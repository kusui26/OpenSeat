## 3. PR の粒度と順番をどう決めたか

ここが本書の中心である。分解の結果だけでなく、なぜその分解になったかを残す。

### 3.1 粒度の原則

**原則 1: 1 つの PR は、レビュアーが答えられる 1 つの問いに対応する。**

「型は 7.2〜7.4 と 7.16 を過不足なく表しているか」「遷移表は図と一致しているか」「割当は 7.6 のとおりか」。問いが 2 つ以上あるなら分ける。問いが立てられないなら、その PR は目的が曖昧である。各 PR の詳細（5 章）は必ず「問い」から始める。

**原則 2: 実装は 300〜500 行を目安にする。テストは別枠で数える。**

目安はコメントと空行を除いた**実装の行数**に適用する。テストを含めると、仕様の表を 1 行 1 テストで写す方針（原則 5、6.3）のぶんだけ膨らみ、目安が意味を失うためである。

実測（PR 1）: 実装 434 行、テスト 665 行、合計 1,099 行。実装は目安どおりだが、テストが 1.5 倍あった。以降の PR も同じ比率になると見込む。

実装が 800 行を超えたら分割を検討する。レビューの質は行数に反比例し、自分でレビューする場合も同じである。逆に 100 行を下回るなら、前後の PR に吸収できないかを考える。**テストの行数が多いこと自体は分割の理由にしない。** 1 行 1 アサーションのテストは平坦に読めるため、複雑なロジックと同じようには効いてこない。

**原則 3: `main` は常に緑で、意味のある状態に保つ。**

途中の PR でも、実装されている範囲では不変条件が成り立ち、テストが通る。「次の PR で直す」前提のコードを入れない。未実装のコマンドは型に存在させない（判別可能なユニオンに足さない）ことで、網羅性チェックを正直に保つ。

**原則 4: 後で捨てる実装を書かない。**

仮実装やスタブを置かない。特に割当アルゴリズムを「とりあえず FIFO」で入れて後から差し替える、という進め方は採らない。テストごと書き直すことになり、二度手間になる。

**原則 5: 宣言 → 振る舞い → 検証 の順に進む。**

CLAUDE.md 3.2 の思想をそのまま日程に落とす。宣言（型・遷移表・不変条件・ポリシー）は 7 章の仕様をコードへ転記する作業であり、レビューは「計画書と一致しているか」の照合になる。振る舞いはその宣言に照らして検証できる。逆順にすると、振る舞いを見ながら宣言を書くことになり、宣言が実装の追認になってしまう。

**原則 6: 検証の道具を早く立ち上げ、以降の PR を自動で叩かせる。**

これが後述する「シミュレータを中盤に置く」判断の根拠である。

### 3.2 順番を決めた 3 つの判断

分解そのものより、順番のほうが結果を左右する。3 つの判断を記録しておく。

#### 判断 1: 宣言（型・遷移表・不変条件）を最初に固める

**代替案**: 歩くスケルトン（受付から退席までの最小の一周）を最初に作り、そこから枝を伸ばす。

**採らなかった理由**: この Phase には I/O が無い。関数呼び出しで組み合わさるだけなので、早期に発見すべき「結合の問題」が存在しない。スケルトンが見つけてくれるものが無い。一方で、宣言を先に置くと、以降のすべての PR が「宣言に照らして正しいか」で検証できるようになる。得るもののほうが大きい。

#### 判断 2: 割当アルゴリズムは 4 番目。最初ではない

**代替案**: 最も難しいロジックなので、型の直後に置いて、設計の誤りを早く見つける。

**検討した結果**: **Phase 1 の本当のリスクは「割当が実装できるか」ではない。** 7.6 には擬似コードと数値例があり、実装は機械的である。本当のリスクは **「既定値が正しいかどうかを、数字で言えるようになるか」** で、これを解消するのはシミュレータであってアルゴリズムの実装ではない。

したがって割当は、依存（型）が揃った直後で、かつ適用（呼び出し）の直前に置く。純粋な選択関数として単独で実装し、状態への反映とは分ける（PR 4 と PR 6 の分離）。これにより 7.6 のエッジケース表 9 行を、状態遷移の都合に邪魔されずにテストできる。

#### 判断 3: シミュレータを最後ではなく中盤（8 番目）に置く ← 本書で最も重要な判断

**当初の案**: シミュレータは検証の道具なので、コアが完成してから作る（13〜15 番目）。

**採らなかった理由が 3 つある。**

1. **シミュレータはファズの実行環境そのものである。** 全体プラン 9.12 が「シミュレータをファズテストとして流し、不変条件違反を検出する」と定めている。最後に置くと、それまでの 7 つの PR は手書きのテストだけで守られることになる。中盤に置けば、以降のすべての PR がランダムなコマンド列で自動的に叩かれる。
2. **Phase 1 の成果物の価値はレポートにある。** 日程が押したときに削られるのは末尾の PR である。シミュレータが末尾にあると、Phase 1 の目的そのものが失われる。中盤にあれば、最悪でも「動くシミュレータと粗いレポート」が残る。
3. **早く数字が出ることの効用。** 割当方式の比較は、コアが 100% 完成していなくても粗い答えが出る。方向が違っていれば早く分かる。

**置ける最も早い位置は、基本の循環が閉じた直後である。** 受付 → 割当 → 呼び出し → 着席 → 退席 → 再割当 が通れば、シミュレータは回せる。それが PR 7 の完了時点なので、PR 8 に置く。

**懸念と対処**: 以降の PR（飛び込み、ノーショー、無断利用）でシミュレータのモデルを拡張する必要がある。ただしシミュレータの骨格（イベントループ、決定的な乱数、分布）は変わらず、増えるのは「どの確率的な判断を注入するか」だけなので、手戻りは小さい。指標の収集と CLI は PR 14 に分けて、骨格を軽く保つ。

### 3.3 分解の副産物として得られること

- **停止しやすい。** どの PR の直後でも中断でき、次に再開しやすい。
- **レビューの問いが計画書に紐づく。** すべての PR が 7 章か 8 章の特定の節に対応する。実装が仕様から離れにくい。
- **`main` の履歴が仕様の実装順になる。** 後から「なぜこの順で作ったか」を辿れる。

### 並行できるもの

一人開発なので基本は直列だが、気分を変えたいときに入れ替えられる組み合わせを挙げておく。

- **2 と 3 と 4** は互いに独立（すべて 1 だけに依存）。順不同でよい。

### 最短の打ち切り線

日程が押した場合にどこで止めれば Phase 1 の価値が残るか。

| 止める位置 | 残るもの | 失うもの |
|---|---|---|
| PR 8 まで | 基本の循環と、それを叩くシミュレータ。Phase 2 の着手は可能 | 異常系、上限、ETA、比較レポート |

**PR 12 で止めるのは避けたい。** 既定値を数字で裏づけることが Phase 1 の目的なので、そこを落とすと実証実験の設定に根拠がなくなる。押した場合は 9・10・11 のいずれかを Phase 2 へ送るほうがよい（これらは実証実験の当日までに間に合えばよい）。

**シミュレータが 8.1 のモデルの食い違いを 1 つ明らかにした。**

8.1 は「到着」の行に 60〜90 組/時を、「席構成」の行に 26 席（2 名席×4、4 名席×3、6 名席×1）を並べて書いている。この 2 つを素直に組み合わせると、3 時間半の到着 約 200 組に対して捌けるのは 50 組ほどで、残りは待ち行列の上限か受付からの絶対上限で落ちる。**到着率は施設全体のもので、100 席（8.1 の比較用の構成）でちょうど釣り合う。**

対応として、区画のシナリオでは到着率を席数の割合まで減らす（`shareOfVenue`）。減らさないとどうなるかは `weekend-overload` シナリオとして残し、過負荷の挙動をいつでも見られるようにした。

**現実には、待ち時間の目安を見た人が登録をやめる**（7.5 の 5「現在 40 分以上お待ちいただく見込みです。登録しますか？」）。この振る舞いが入れば過負荷は自然に頭打ちになるが、待ち時間の推定が要るので PR 13 の課題とした。

**この PR で決めたこと**

- **乱数の流れを目的ごとに分けた。** 8.2 は同じ負荷に方針を取り替えて比べる。1 本の列を全員で使うと、方針によって乱数を引く回数が変わり、そこから先がすべてずれる。「待ち時間が縮んだのは方針のおかげか、たまたま空いていた日だからか」が区別できなくなる。さらに **1 組の性質（人数・滞在時間・歩く速さ・ノーショーの目）は、その組だけの流れからまとめて引く**ので、何組目の誰がどんな人かが方針によらず固定される（共通乱数）
- **ノーショーは「目」だけを先に引き、比べる相手を呼び出しの時点で決める。** 8.1 は「待ち時間が長いほど上昇」と言うが、待ち時間は呼ばれるまで分からない。目を先に引いておけば、待ち時間が変わっても「その人が引いた目」は変わらない
- **利用者はイベントに反応する。** 呼び出されたことを知るのは `TicketCalled` が出たときで、これは Phase 2 のサーバが通知を出すのと同じ形である。シミュレータだけが知っている事実を覗かないので、現実に起こりえない筋書きにならない
- **受付時間は到着率の定義域から導く。** 別々に持つと、区間を足したときに受付時間を直し忘れ、最後の区間の率がそのまま延長される
- **「向かっています」と「準備OK」も出す。** プランの列挙（受付・割当・呼び出し・着席・退席・ノーショー）には無いが、7.7 の 3〜6 の循環をたどるには要る。**入れないと、歩くのが遅い人（ホールド 7 分に対し 3 割弱）が全員そのまま消える。** 押す率は 8.1 に無いので「まだ着いていなくて来る気がある人は押す」とした
- **指標は返さない。** 待ち時間や稼働率は PR 14 の責務で、ここはイベントを素のまま返す。先に固めると、指標の定義を変えるたびにシミュレータを触ることになる

**シミュレータの再現性を CI で守るようにした。** `packages/core/sim` では `Math.random()` と実時刻を禁じ、`scripts/check-architecture.mjs` の 3 つ目の検査として落とす。種から導かない乱数が 1 か所でも混ざると、同じシードで同じ結果にならなくなり、比較そのものが成り立たなくなるため。CI の自己点検にも、意図的な違反を検知できることを確かめる手順を足した。

**いまの限界（PR 10 で解消する）**: 8.1 の退席申告率 60% をそのまま使うと、**8 卓すべてが埋まったまま戻らなくなる**。申告しない人が通る「p90 の問いかけ → 無応答 → 確認要」の経路（7.11 の 2 と 5）がまだ無いためで、シミュレータはその様子を隠さずに出す。申告率 100% なら 47 組中 40 組が使い終わる。**PR 10 を待つ理由が数字で出た形になった。**

**規模**: 実装 527 行（目安 550 行）、テスト 869 行・131 テスト。累計 952 テスト。`packages/core/sim` を `src` の外に置いたので、`tsconfig`・`vitest`・`eslint`・アーキテクチャ検査の設定を足した（CLI が `process` と `console` を使う PR 14 のため、`src` の中には置けない）。

#### PR 9 — 座席 QR の全分岐と飛び込み

> **問い: 7.8 の表の 10 行すべてが実装され、テストされているか。**

**出典**: 全体プラン 7.8、7.12、7.11 の 3 層目
**依存**: PR 7 ／ **見積**: 6h ／ **目安**: 500 行

**実装**

座席 QR は受付・着席・退席・報告のすべてを兼ねる。**読み取った人の状態とテーブルの状態の組み合わせで振る舞いが決まる**ため、この分岐を 1 か所にまとめ、7.8 の表と 1 対 1 で対応させる。

```ts
/** 座席 QR を読んだときに、その人に何を見せ、何ができるかを決める。 */
export function resolveTableScan(
  state: VenueState, tableId: TableId, ticketId: TicketId | null, now: Timestamp,
): TableScanOutcome;
```

`TableScanOutcome` は判別可能なユニオンにし、7.8 の表の行と 1 対 1 にする。画面の文言は Phase 2 だが、**どの結果になるかは core が決める**（CLAUDE.md 3.1: ビューは業務判断をしない）。

実装する分岐（7.8 の表の順）:

1. 割り当てられた席 → 着席（PR 7 で実装済み）
2. 別の席に割当、その席が空いていて人数が収まる → 席の変更（`allow_table_swap`）。元の席は `FREE` に戻る
3. 別の席に割当、その席は使えない → 自分の席を案内するだけ
4. `WAITING` で、空席かつ人数が収まり、その席を待つ人が他にいない → 即着席（割当の前倒し）
5. `SEATED` でこの席 → ご利用中の画面
6. チケットなし、空席、収まる待ちがいない → **飛び込み着席**（7.12）
7. チケットなし、空席、待ちがいる → 受付へ誘導
8. チケットなし、`HELD` → 呼び出し中の席である旨
9. チケットなし、`OCCUPIED` / `OCCUPIED_UNKNOWN` → 使用中である旨、空席なら報告できる
10. 割り当てられた席だが誰かが座っていた → **席が塞がっていた報告**。テーブルは `OCCUPIED_UNKNOWN`、チケットは `WAITING` に戻り `conflictPriority` が立つ

**テスト**

**7.8 の表の 10 行を、1 行 1 テストで写す。** これがこの PR の完了条件そのものになる。加えて、

- 席の変更で元の席が解放され、次の人に渡ること
- `allow_table_swap = false` のとき変更が拒否されること
- 飛び込み着席で定員を超える人数が拒否されること
- 「席が塞がっていた」報告の後、その人が最優先で次の席に案内されること
- `conflictPriority` が同じ `priorityAt` の他者より前に来ること（PR 4 の選択と結合するテスト）

**完了条件**: 7.8 の表の 10 行すべてにテストがあり、緑。

**実装後の記録（2026-09-19）**

**7.8 の表は 10 行だが、答えを持つべき組み合わせは 63 通りあった。**

7.8 が書いているのは主な組み合わせだけで、席 7 状態 × 読み取った人 9 通り（チケットなし ＋ 8 つの状態）のうち 10 行しか埋まっていない。**同じ QR が受付・着席・退席・報告のすべてを兼ねる以上、答えの無い組み合わせが 1 つでもあると画面が固まる。** そこで分岐を 2 つの総当たりの表（`TableStatus` を鍵にしたもの、チケットの状態を鍵にしたもの）として書き、63 通りすべてを試すテストを置いた。7.8 に無い 5 つの結果を足してある。

| 足した結果 | いつ | なぜ 7.8 に無いか |
|---|---|---|
| `keep_waiting` | 待っているが、その席は順番を崩す | 7.8 は「座れる場合」しか書いていない |
| `resume_first` | 保留中 | 保留は 7.7 の話で、7.8 の表には出てこない |
| `seated_elsewhere` | 着席中に別の席を読んだ | 起こりうるが書かれていない |
| `turnover` | 片付け中の席 | `TURNOVER` は 7.6 の状態 |
| `not_managed` | 対象外の席 | `DISABLED` は 7.14 の状態 |

**実装の誤りを 1 つ、書いている途中で見つけた。**

> **画面に出す操作の判定と、コマンドのガードを別々の式で書いていた。**

「この席に変更できます」と出したのに `SWAP_TABLE` が拒否される、あるいはその逆が起こりうる形だった。とくに前倒しの着席では、画面側が `chooseAssignments`（施設全体の割当）、ガード側が `pickCandidate`（その席の選択）を見ていて、**同じ定員の席が 2 つあるときに答えが割れた**。判定を `machine/guards.ts` の 1 か所に寄せ、画面もコマンドと同じガードに聞く形に直した。

**ファズが性質の前提の抜けを見つけた。** 「空席が無い施設では、時間の進め方によらず同じ状態になる」という PR 6 の性質は、`CONFIRM_FREE`（使用中の席を空席に戻す報告）を生成器に足した瞬間に落ちた。**前提の「空席が無い」を、コマンドが途中で壊していた。** 生成器を待ち行列の側のコマンドだけに絞って直した。

**この PR で決めたこと**

- **`resolveTableScan` は問い合わせで、状態を変えない。** 何を見せ、どの操作を出すかを返すだけで、押したときに何が起きるかは `apply` が決める。返す操作は必ず実在するコマンドの種別にしてあり、画面が独自の操作を足せない
- **「この席を待つ人が他にいない」を「いまこの席に割り当てるなら自分が選ばれる」と読んだ。** 字面どおり「ほかに収まる人が 1 人もいない」と読むと、混んでいる施設では誰も前倒しできない。7.8 が括弧で書いている「待ち順序を崩さない」が狙いなので、割当の選択（7.6）をそのまま使う
- **席を移しても呼び出しの期限は動かさない。** すでにその席の前に立っている人が、さらに時間を得る理由が無い
- **飛び込み着席は、その席の定員だけを見る。** 施設全体の最大人数ではない。読んだ席に収まるかどうかがすべてである
- **飛び込み着席は受付の開閉を見ない。** 受付を閉じたあとでも、席が使われていることを記録できるほうが状態は正確になる（7.12 の (a)）。待ち行列にも入らないので `max_queue_length` にも触れない
- **着席中の人を第三者が追い出せない。** 「空席になっていたら報告」（`CONFIRM_FREE`）は、誰が座っているか分からない席（`OCCUPIED_UNKNOWN`・`NEEDS_CHECK`）にしか効かない。遷移表に `OCCUPIED` からの宣言が無いことがそのまま守りになっている
- **対象外の席でも、そこに座っている人は退席できる。** 分岐の順序で、着席中の判定を対象外の判定より先に置いた。閉じ込めない
- **「待ちへ戻る」に理由を持たせた。** ノーショーの `requeue_back` は順番を **末尾へ**、席が塞がっていた報告は **先頭へ**。向きが正反対なので、`TicketRequeued` に `reason` を足して区別できるようにした

**シミュレータに飛び込みと無断利用を足した**（PR 8 が「PR 9 で足す」としていた分）。8.1 の「無断利用 0.2 件/卓/時」を、**座席 QR を読む人（飛び込み着席）と読まない人（システムから見えないゴースト）に分ける**モデルにした。読む割合は 8.1 に無いので 0.5 を初期値に置き、差し替えられるようにしてある。

> **7.12 の狙いが数字で出た。** 誰も座席 QR を読まないと「案内された席が塞がっていた」事故が毎回起きる。全員が読めば 1 件も起きない。

**規模**: 実装は `scan/resolve.ts` 128 行＋コマンド 6 つとガード 2 つ。テスト 852 行・134 テストを 2 ファイルに追加し、累計 1,094 テスト。**ガードはチケット 10 個中 9 個が実装済み**になった（残るのは `hardLimitMode`・PR 10）。

**PR 10 へ送ること**: 7.11 の 3 層目で「空いている可能性が高い席」に案内された人が、その席が空だと確かめたあと、**その席を確実に得られるか**。いまは `CONFIRM_FREE` で席が空席に戻り、通常の割当にかかるので、ほかの人に取られうる。7.11 が言う「現状の『歩き回って探す』より悪くならない」を満たすには、確かめた人に渡す仕組みが要る。

#### PR 10 — 時間上限と整合性回復

> **問い: 7.10 の 3 モードが切り替わるか。7.11 の 5 層のうちロジックが担う 3 つ（問いかけ、確認要の割当、時間経過による整理）が動くか。**

#### PR 11 — 運用時間帯とモード切替

> **問い: 運用時間の開始と終了で、席が正しく切り替わるか。全席解放が安全に動くか。**

**出典**: 全体プラン 7.14
**依存**: PR 5 ／ **見積**: 4h ／ **目安**: 350 行

**実装**

- **運用スケジュール**: 曜日と時間帯の指定（`managed_schedule`）。施設のタイムゾーンで評価する。core は時刻を UTC のミリ秒で受け取るため、タイムゾーンの変換は境界側で行い、core には「運用時間内かどうか」を判定できる形（施設のローカル時刻に変換済みの分数など）で渡す
- **運用開始**: 対象席が `DISABLED → FREE`
- **運用終了**: `join_cutoff_before_close_min` 前に受付を停止。終了時刻に残った `WAITING` / `PAUSED` を施設都合でキャンセル。`SEATED` はそのまま（座り続けてよい）
- **手動の切替**: スタッフによる運用 ON / OFF。スケジュールより優先する
- **全席解放**: 緊急時にすべてのチケットを `CANCELLED(施設都合)` にし、すべてのテーブルを `DISABLED` にする

**テスト**

- スケジュールによる開始と終了
- 受付停止のタイミング
- 終了時に `SEATED` のチケットが巻き込まれないこと
- 手動の切替がスケジュールより優先されること
- 全席解放の後、不変条件が成立していること
- 運用中に席を対象外にしたとき、`disableAfterCurrent` で現在の利用が終わってから反映されること（7.6 のエッジケース）

**完了条件**: 運用時間帯の開閉と全席解放がテストされ、シミュレータのシナリオが運用時間を持てるようになる。

**実装後の記録（2026-09-19）**

**この PR の設計はひとことで言える。**

> **運用終了を、ホールドの期限や保留の期限とまったく同じ「期限」にした。**

`managed_schedule`（曜日と時間帯）の評価にはタイムゾーンが要るが、core は時刻を UTC のミリ秒でしか受け取らない（9.4）。そこで **変換は境界側に置き、core には「この営業回が終わる絶対時刻」だけを渡す**（`VenueState.closesAt`）。`schedule.ts` はその計算を提供する純粋な層で、状態も持たなければ `VenueState` にも入らない。

この形にしたおかげで、運用終了は個別のタイマーを持たずに処理でき、**再起動しても取りこぼさず、`tick` の刻み方によらず同じ結果になる**。シミュレータも時計を進めるだけで 7.14 を再現できる。

**7.14 が書いていなかったことを 3 つ決めた。**

| 決めたこと | なぜ |
|---|---|
| **`CALLED` の人は締め出さない** | 7.14 は `WAITING`/`PAUSED` と `SEATED` にしか触れていない。7.4 が「利用中の席（`HELD` を含む）は現在の利用が終わってから外す」としているので、確保した席へ向かっている人を終了時刻ちょうどで取り消す理由が無い |
| **使われていた席は、空いた時点で運用から外れる** | 終了時刻にすぐ外すのは使っていない席だけ。着席中の人の席を取り上げないという 7.14 の主旨をそのまま席側にも通した |
| **「対象席から外す」と「運用時間外」は別のこと** | 前者は管理者の設定（`enabled`）、後者はいまの時間帯（`DISABLED`）。混ぜると、閉店で外れた席が翌日戻らなくなる |

**終わり方 10 通りが、すべて到達可能になった。** 最後に残っていた `venue_closed` が運用終了と全席解放で作られるようになり、ファズの性質「終わり方は宣言されている 10 通りのいずれかになる」が、除外なしで緑になった。PR 7 から 4 本の PR をまたいで追ってきた穴がここで閉じた。

**不変条件を 1 つ足した**（12 個目）。「受付を開いているなら運用している」。逆は成り立たない — 運用終了の手前では、運用しながら受付だけを閉じている。

**全席解放は、運用していなくても通る。** CLAUDE.md 8 章が「『全席解放』操作の動作は常に保てるように」と書いているためで、障害時に自由席へ戻す手順がシステムの復旧より優先される。着席していた人は `DONE`（利用として扱う）、待っている人と呼び出し中の人は `CANCELLED`（施設都合）になる。

**ファズとテストが、実装の誤りを 2 つ見つけた。**

| # | 見つけたもの | 何が起きていたか |
|---|---|---|
| 1 | イベントの時刻が、コマンドより前になる | 空席を「対象外にする」と、出口（`settle`）が **その席が空いた時刻**で外していた。外すと決めるより前の時刻がイベントに載る。空席はその場で外す形に直した |
| 2 | **飛び込み着席した人の席が、永久に埋まったままになる** | シミュレータが `WALK_IN` を送ってから「この人は誰か」を覚えていた。`TicketSeated` への反応はコマンドの中で走るので間に合わず、**退席の申告も、実際に立ち上がる時刻も記録されない**。その人が「まだ利用中」と答えると 7.11 の回復も閉じるので、席は最後まで戻らない |

2 つ目は PR 9 で飛び込み着席を入れたときからあった欠陥で、**運用終了のテスト（「終了後に生きたチケットが 1 枚も残らない」）が初めて表に出した**。7.11 の回復が効いているあいだは症状が出ず、運用終了という別の出口を足したことで、戻らない席が 1 卓だけ残る形で見えた。

**この欠陥を直したので、PR 10 で出した数字が少し動いた。** `weekend-peak`・申告率 60%・種 2026 で、**3 層目なしの「使い終わった組」が 28 → 32 に**（3 層目ありは 39 のまま）。3 層目の効きは試した 4 シードすべてで正の向き、という結論は変わらない。

**`VenueClosed` から「誰を取り消したか」を落とした。** 最初は一覧を載せていたが、運用終了を 1 枚ごとの期限として処理する設計では、時間で閉じたときに一覧が空になる（そのときにはもう取り消し済み）。**同じことを 2 か所に持つと、片方だけが正しい状態が作れてしまう。** それぞれの `TicketEnded`（`endReason` は `venue_closed`）が理由つきで語るので、数えたい側はそちらを読む。

**この PR で決めたこと**

- **運用終了の取り消しは、1 枚ごとの期限として処理する。** 施設の側でまとめて取り消すと、運用終了より早いホールドの期限が後回しになり、`tick` の刻み方で結果が変わる
- **同じ時刻に自分の期限と運用終了が重なったら、施設都合のほうを採る。** 取り消し（`CANCELLED`）は期限切れ（`EXPIRED`）より説明がやさしく、利用者に厳しくない側だから
- **手動の切替とスケジュールは、core から見れば同じ操作である**（`OPEN` / `CLOSE`）。7.14 の「手動を優先させる」は、境界側のスケジューラが手動の指示を上書きしない、という形で実現する。core が「いまどちらの指示か」を覚えると、状態が 1 つ増えて再起動のたびに食い違う
- **席を対象から外す操作と、戻す操作を対にした。** 片道だけ用意すると、誤って外した席を戻す手段が無くなる
- **シミュレータのシナリオは、既定で運用終了を持たない。** 8.1 はピークの 3 時間半を切り出したもので、その先に閉店があるかは書かれていない。入れると終了時刻に残った人が取り消され、待ち時間や回転率の見え方が変わる。運用時間を見たいときだけ `withClosing()` で足す

**用意しなかったもの**: `managed_schedule` を `VenueState` に持たせること。core の中で読むものが 1 つも無く、持たせるだけで再起動時の整合（設定が変わったらどうするか）を抱えることになる。曜日と時間帯の設定は施設の設定として境界側が持ち、core には解決済みの終了時刻だけが来る。

**規模**: 実装は `schedule.ts` 137 行、`machine/venue.ts` 201 行、既存への追加が約 300 行。テストは `venue.test.ts` 551 行、`schedule.test.ts` 150 行の新規 2 ファイルと既存への追加で、**累計 1,280 テスト**（PR 10 から +94）。ファズの生成器にも 5 つのコマンド（`OPEN` / `CLOSE` / `RELEASE_ALL` / `DISABLE_TABLE` / `ENABLE_TABLE`）を足した。

**PR 12 へ送ること**: 遷移表の網羅と到達可能性。**宣言だけあって到達できない遷移は、この PR で無くなったはず**だが、それを機械的に確かめるのが PR 12 の仕事である。`tick` の性質のうち「時間の進め方によらず同じ状態になる」は、運用終了が入っても条件付きの形（コマンドが挟まらず、空席が無いとき）のままでよいかを見直すこと。

#### PR 12 — `tick` の性質と遷移表の網羅

> **問い: 時間をどう飛ばしても、何度呼んでも、状態は壊れないか。宣言した遷移は全部動くか。**

**出典**: 全体プラン 9.4、9.12 ／ CLAUDE.md 3.4
**依存**: PR 6、9、10、11 ／ **見積**: 5h ／ **目安**: 400 行

`tick` は PR 6・10・11 で少しずつ育つ。この PR は新機能ではなく **固めるための PR** である。

**実装**

- 時刻起因の遷移を 1 つの `tick` に集約し、評価順を明示する（期限切れ → 自動整理 → 割当、の順）
- 大きな時間の飛びへの対応。サーバの再起動や時計のずれで、10 秒ではなく 1 時間飛ぶことがある。**期限を「経過した回数」ではなく「絶対時刻の比較」で判定する**設計になっていることを確認し、飛んでも取りこぼさないことを保証する
- **遷移表の網羅性の検査**: 宣言されたすべての遷移が実装から到達可能であること、ガード名の集合が実装済みガードの集合と一致すること

**テスト**

- **冪等性**: 同じ時刻で `tick` を 100 回呼んでも状態が変わらない（性質テスト）
- **時間の飛び**: 1 時間を、10 秒刻みで 361 回進めた場合と、1 回で進めた場合の結果が一致する（ただし途中で発火するイベントの個数は一致しなくてよい。到達する状態が一致すること）
- **単調性**: 時刻を戻す `tick` が拒否されること
- **網羅性**: `TICKET_TRANSITIONS` と `TABLE_TRANSITIONS` の全行が、実際のコマンドまたは `tick` で到達できること。到達できない行があれば、仕様の誤りか実装漏れなので落とす
- **ガードの一致**: 遷移表が参照するガード名と、実装されたガードの集合が一致すること

「1 時間を 1 回で進めた場合と 361 回で進めた場合が一致する」というテストは、実装が経過時間の累積ではなく絶対時刻で判定していることを保証する。これは Phase 2 でサーバが再起動したときの正しさに直結する。

> **一致するのは「空席が無いとき」だけである。** PR 6 のファズがこれを見つけた。席が空いたことは期限の時刻で刻めるが、**次の人を呼べるのは `tick` が走った時点**なので、飛ばし方で呼び出しの時刻が変わる。遡って呼び出すと、届いていない呼び出しのホールドがすでに切れていることになり、利用者に不利になる。**取りこぼしではなく、設計上そう決めている。** そこで、飛びに対する保証は 2 本に分ける。
>
> 1. **空席が無ければ、刻み方によらず同じ状態に落ち着く**（等価性）
> 2. **どんな場合でも、一度の `tick` で来ている期限がすべて片づく**（取りこぼしの不在）
>
> 2 つ目が「再起動しても取りこぼさない」の本体で、こちらは条件なしに成り立つ。

**完了条件**: 冪等性と時間の飛びの性質テストが緑。遷移表の全行が到達可能（到達しない行があるなら、理由が書かれて数え上げられている）。

**実装後の記録（2026-09-19）**

**固めにきた PR で、2 つのことが出た。** 遷移表の **1 行が実態から浮いていた**こと、そして **席が永久に塞がる筋書きが 1 つ残っていた**ことである。後者は、PR 10 が書いた性質が PR 11 のあとで **10 回に 3 回ほど落ちる**ようになって見つかった。

> **運用が終わった施設で「まだ利用中」と答えた人の席は、永久に塞がったままになる。**

道筋はこうだった。運用終了で待っている人が全員取り消される → `limit_only_when_waiting` が立っているので上限が効かなくなる → 一度「まだ利用中」と答えた人には問いかけが二度と出ない（7.11 が「1 回」と書いていた）→ **`OCCUPIED` から出る道が 1 本も残らない**。その席は次の `OPEN` でも戻らない（運用開始が戻すのは `DISABLED` の席だけ）ので、**日をまたいで 1 卓失われる**。

**直し方は 7.11 の側にした。** 問いかけを「答えたら、そこから測り直してもう一度」に変える。7.11 の「1 回」と、同じ 7.11 の「最悪でも席が永久に塞がらない」が食い違っていたので、**保証のほうを残した**。答える手間は 1 タップで、答えているかぎり席はその人のものなので、繰り返し聞くほうが利用者の利益にもかなう。全体プラン 7.11 の 2 層目を書き直した。

実装は期限の式 2 つだけで済んだ。「答えたか」ではなく「**最後の問いかけより後に答えたか**」で見るようにし、答えの時刻は消さずに残す（上限の超過を抑えるのに要る。PR 10 の直しを壊さない）。

**遷移表 61 行のうち、60 行に「実際に通る証拠」を置いた。**

証拠は 1 行につき 1 つ、`reachability.test.ts` にある。それぞれが 2 つのことを同時に示す。

1. **その事象を起こす道がある。** `apply` か `tick` を 1 手動かして、対象が `from` から `to` へ動くのを見る
2. **その行が採られる。** 同じ（状態、事象）に複数の行があっても、`ticketTransitionRow` / `tableTransitionRow` がまさにその行を返す

証拠の無い行は落ちる。**遷移を足したら、ここに証拠を足さないと通らない。**

**残る 1 行は、この版では通らない。**

> **`FREE --CHECK_IN_EARLY--> OCCUPIED`（7.8 の 4 行目、空席への前倒し着席）**

**割当がコマンドのたびに必ず走るので、「収まる空席があるのに待っている人が残る」という状態が作れない**（不変条件 `no_starvation`）。前倒しの着席はまさにその状態でしか成り立たないので、空席に対しては決して通らない。空席の QR を読んだ待ち人は、その瞬間にはもう呼ばれていて、通常の着席（7.8 の 1 行目）になる。

**行は消さずに残した。** 7.8 が書いている画面は実在するし、`CHECK_IN_EARLY` 自体は「確認要」の席で通っている（7.11 の 3 層目）。消すと、割当の走り方を変えたときに宣言ごと失われる。代わりに **「通らない理由」を書いて数え上げる**形にし、`tick.property.test.ts` に「空席に前倒しで座れる人は残らない」という性質を置いて、主張のほうを検証している。全体プラン 7.8 にもこの読み替えを書き足した。

**時計の単調性を実装した**（プランの「単調性」）。

状態が「最後に進んだ時刻」（`clockAt`）を持ち、`apply` と `tick` が入口で確かめる。戻っていれば `CLOCK_WENT_BACKWARD` で拒否し、**`isDefect` が真を返す側**に置いた（利用者の操作の誤りではなく、実装の誤りだから）。

なぜ要るか。**期限の判定はすべて絶対時刻の比較でできているので、時計が戻ると、いったん過ぎた期限がまた「これから」に戻る。** ホールドが切れて保留に戻った人に、もう一度ホールドの期限が生える。壊れ方が静かなので入口で落とす。同じ時刻は通す（冪等性を保つため）。

**「時間の飛びに強い」の保証を、2 本に分けた。**

プランは「1 時間を 361 回に分けても 1 回でも、同じ状態になる」と書いていたが、**これは条件つきでしか成り立たない**（PR 6 のファズが見つけていた）。席が空いたことは期限の時刻で刻めるが、**次の人を呼べるのは `tick` が走った時点**である。そこで、

| 保証 | 条件 |
|---|---|
| 刻み方によらず同じ状態に落ち着く | 空席が無いとき（あいだにコマンドも挟まらないとき） |
| **一度の `tick` で、来ている期限がすべて片づく** | **条件なし** |

2 つ目が「再起動しても取りこぼさない」の本体で、こちらは無条件に成り立つ。`tick` のあと、どのチケット・どの席にも「もう来ているのに処理されていない期限」が残らないことを性質として書いた。

**遡って呼び出さないのは、決めごとである。** 1 時間止まっていた施設が再開したとき、席が空いた 8 分の時点に遡って呼び出すと、**届いていない呼び出しのホールドがすでに切れている**ことになる。再開した時点で呼び直すほうが利用者に不利でない（CLAUDE.md 2.5）。テストで両方の筋書きを並べて、違いが出ることそのものを固定した。

**`tick` の評価順を、テストで固定した。**

> チケットの期限 → 施設の期限 → 席の期限 → 割当 → 不変条件の検査

1 回の `tick` でこの 4 段すべてが起きる筋書きを作り、イベントの並びで順序を押さえてある。**席の期限を割当より先に明かす**のがここの肝で、逆にすると空いているはずの席が次の人に渡らない（PR 7 で決めたこと）。

**選び方の規則を 1 か所にまとめた。** 遷移表から「いま採られる行」を返す `taken()` を切り出し、`transit()` もそれを使うようにした。網羅性の検査と実際の遷移が **同じ関数**を見るので、答えが割れない。

**この PR で決めたこと**

- **到達しない行は、消すか、理由を書いて数え上げるかのどちらかにする。** 黙って残すと表が腐る。数え上げておけば、新しく到達しなくなった行が増えたときに落ちる
- **時計が戻るのは実装の誤りとして扱う。** 利用者向けの文言に変える対象ではなく、記録して調査する対象である
- **冪等性は 100 回で確かめる。** 2 回で足りるように見えるが、「経過した回数」で進む実装はここで必ず落ちる

**規模**: 実装は `machine/clock.ts` 36 行と、`transit.ts` / `transition.ts` への追加が約 40 行。**新しい振る舞いはほとんど足していない**（`tick` の入口 2 行と `settle` の出口 1 行だけ）。テストは `reachability.test.ts` 938 行、`clock.test.ts` 158 行の新規 2 ファイルと、`tick.test.ts` / `tick.property.test.ts` / `guards.test.ts` への追加で、**累計 1,443 テスト**（PR 11 から +163）。

**ファズについて言えること。** PR 4 から 11 までは毎回ファズが何かを捕まえてきた。この PR で足した検査（網羅性、時計、取りこぼしの不在）は **1 つも新しい欠陥を出さなかった**。出したのは、**既にあった性質が、生成器にコマンドが増えたことで初めて破れた**ぶんである。性質を増やすことと、性質を流す入力を増やすことは、どちらも要るということがはっきりした。

**PR 13 へ送ること**: 待ち時間の推定（ETA）。PR 8 が積み残した「目安待ち時間が長いと登録をやめる」（7.5 の 5）は、ETA が入って初めてシミュレータで表現できる。**過負荷のシナリオ（`weekend-overload`）が現実より厳しく出ているのはこのためで**、PR 13 のあとで測り直すこと。

#### PR 12.6 — 確認要の席を空席に戻せる人を決める（差し込み）

> **問い: 人のチケットを終わらせる報告を、誰に許すか。**

**出典**: 全体プラン 7.4・7.8 の 9 行目・7.11 の 3 層目・7.15 ／ [ADR-0011](adr/0011-who-may-free-an-uncertain-seat.md)

PR 12.5 が「別に決める」として送った食い違いに答えた PR。選択肢と理由は ADR-0011 にある。

**まず、何が起きるかを確かめた。** 問いかけに答えないまま「確認要」に落ちた席で、**チケットを持たない通りすがりの人が「空いていました」を押すと、座っている人のチケットが終わる**（席は `FREE`、チケットは `DONE`／`auto_release`）。計画書は 7.8 の 9 行目が「誰でも」、7.4 の図と 7.15 が「スタッフか案内された本人だけ」で割れていた。

- 拒否コード `STAFF_ONLY` を足した（15 → 16 個）
- `handleConfirmFree` に前提条件を 1 つ。**遷移表を引いたあとに見る** —— 着席中の席のように誰も戻せない席では「表に無い」が正しい理由で、スタッフなら通るかのような拒否を返さないため
- 座席 QR の画面が、記録の残る席では「空いていました」を出さない（`reportActions`）
- 7.4 の図の 3 つのラベル、7.11 の 3 層目、7.15 の行を書き直した

**生成器を強くした（この PR でいちばん効いたこと）**

画面とコマンドが食い違わないことは、PR 10 の性質「画面に出した操作は必ず通る」が見ているはずだった。**わざと画面側だけ元に戻して流したところ、素通りした。** `resolve.property.test.ts` の生成器が「着席の記録が残ったまま確認要に落ちた席」を作れておらず、200 回まわして 1 度も出ていなかったためである（呼び出し・着席・時間の経過がすべて噛み合わないと作れない）。

出発点にその席を置くようにしたら、同じ壊し方で落ちるようになった（`needs_check/CONFIRM_FREE: STAFF_ONLY`）。**7.11 の 3 層目は画面の分岐がいちばん込み入っているのに、そこが 1 度も試されていなかった。**

PR 12.5 に続いて 2 度目である。**性質を増やすだけでは足りない。その性質を流す入力が目的の状態へ届いているかを、壊して確かめること。**

**この PR でやらなかったこと**

- スタッフ画面の「空席にする」（7.11 の 4 層目）は Phase 2。これが無いと、記録の残った席を人の手で戻せない

**出典**: 全体プラン 7.13
**依存**: PR 7 ／ **見積**: 4h ／ **目安**: 350 行

**実装**

`packages/core/src/eta.ts`。7.13 の v1 アルゴリズムをそのまま実装する。

1. 人数 `p` が収まるテーブル集合 `T_p` を求める
2. 各卓の推定残り時間 `r_t` を求める。`FREE` / `TURNOVER` は 0、`HELD` はホールドの残り ＋ 平均滞在、`OCCUPIED` は `max(0, D − 経過時間)`（`D` は平均滞在時間、初期値 35 分）
3. `r_t` を昇順に並べ、自分より前にいて `T_p` を取り合う組数を `k` として、`k+1` 番目の `r_t` を目安とする
4. 表示は 5 分刻みの幅（`eta_display`）と「前に `k` 組」

`NEEDS_CHECK` と `OCCUPIED_UNKNOWN` の席をどう数えるかを決める必要がある。**7.13 に明記が無いので、この PR で決めて ADR に残す。** 推奨は「`NEEDS_CHECK` は空く可能性が高いので `OCCUPIED` の半分の残り時間として数え、`OCCUPIED_UNKNOWN` は `OCCUPIED` と同じに数える」。悲観側に寄せるという 7.13 の原則に従う。

**シミュレータに足すもの**: 7.5 の 5 が言う「目安待ち時間が長い場合は登録前に確認する」振る舞い（登録をやめる人）。PR 8 の時点では入れていないので、過負荷のシナリオでは待ち行列が上限まで伸びきる。目安時間が出せるようになったら、`long_wait_confirm_min` を超えたときに一定の割合が登録をやめる形でモデル化する。

**テスト**

- 空席があるときは「5 分未満」
- 前に k 組いるときに k+1 番目の席の残り時間が返ること
- **単調性**: 状態が変わらないまま時間が進むと、ETA は減るか同じ（増えない）
- **悲観性**: 返される目安が、幅の下限ではなく上限寄りであること
- 自分の人数が収まる席が 1 つも無いとき（定員超過）の扱い
- 5 分刻みの丸め（12 分 → 「10〜15 分」）
- シミュレータと突き合わせ、**予測と実績の差（MAE）を測る**。数字は PR 15 のレポートに載せる

最後の項目が重要で、ETA の精度を「良さそう」ではなく数字で言えるようにする。

**完了条件**: 7.13 の v1 が実装され、単調性の性質テストが緑。MAE が測れる。

## 6. すべての PR に適用する横断ルール

各 PR の詳細には書かない。全部に効く。

### 6.1 進め方

1. **ブランチを切る。** `feat/p1-NN-短い説明`（例 `feat/p1-04-allocation-choose`）
2. **PR 本文に、対応する全体プランの節番号と「問い」を書く。** PR テンプレートの「影響範囲」で `packages/core` にチェックを入れる
3. **`pnpm verify` を通してから PR を出す。** 通っていないなら、通っていないと明示する
4. **マージはマージコミット**（squash しない）。`main` に直接 push しない

### 6.2 実装

- **`apply` の出口で必ず不変条件を検査する。** 破れていたら変更を破棄して拒否する。握り潰さない
- **遷移表にない遷移を起こさない。** 状態を直接書き換えるコードを書かない
- **新しいコマンドを足したら、ファズの生成器にも足す。** これを忘れると、そのコマンドはランダムテストの対象外になる
- **`packages/core` の純粋性を守る。** 時刻は引数、乱数は外から、I/O は無し。CI が検査する
- **運用パラメータを増やしたら 7.16 の表にも足す。** 表とコードの `Policy` が 1 対 1 であることは PR 1 のテストが守る

### 6.3 テスト

- **仕様の表は、1 行 1 テストで写す。** 7.6 のエッジケース表、7.8 の分岐表、7.16 のパラメータ表。人間が目で照合できる形にする
- **境界値を必ず書く。** 期限ちょうど、定員ちょうど、待ち 0 組、待ち上限
- **性質テストは、手書きのテストの代わりではなく追加。** 具体例は読んで分かり、性質は見落としを拾う。両方要る
- **テストの名前は日本語で、仕様の文言に寄せる。** 「4 名席が空いたとき、10 分未満の差なら 4 名組を優先する」のように書けば、テスト一覧が仕様書になる

### 6.4 ドキュメント

- **設計上の判断をしたら ADR を書く。** 1 ファイル 1 決定。迷ったら書く
- **全体プランと食い違いを見つけたら、実装を進める前に全体プランを直す。** 実装が仕様から静かに離れるのを防ぐ
- **本書（Phase 1 プラン）も更新する。** 見積もりが外れた、PR を分けた、順番を入れ替えた、はすべて記録に値する

## 7. 設計上の先決事項

実装を始める前に決めておくこと。迷いながら書くと後で揃わなくなる。

### 7.1 乱数を core に持ち込まない

`packages/core` は `Math.random()` を使えない（ADR-0004、CI で検査）。したがって **core の `apply` と `tick` は完全に決定的**にする。

確率的な要素はすべて呼び出し側に置く。「この人はノーショーする」「滞在は 32 分」という判断はシミュレータが下し、core には **コマンド、または何も起きないこと** として現れる。Phase 2 のサーバでは、それが実際の利用者の操作になる。

この設計により、シミュレータとサーバは同じ core を、同じ決定性で動かせる。

### 7.2 ID は外から渡す

ID の生成には乱数が要るため、core では作れない。`JOIN` コマンドは `ticketId` を含む。生成はシミュレータとサーバの責務。

表示コード（`A-23`）は例外で、状態から決定的に導けるため core が採番する。

### 7.3 失敗は例外ではなく `Result`

`apply` は `Result<Decision, Rejection>` を返す。理由はコードで表し、文言は Phase 2 の i18n に置く。純粋関数の失敗を型で表せ、呼び出し側が握り潰しにくい。

`assertInvariants` が投げる `InvariantError` だけは例外のままにする。これは「起きてはならないこと」で、呼び出し側が捕捉して変更を破棄する。通常の拒否（定員超過など）とは種類が違う。

### 7.4 状態は配列で持つ

`readonly Table[]` と `readonly Ticket[]`。規模（席 20〜100、有効チケット 200 程度）に対して線形走査で十分で、7.6 の擬似コードにも素直に対応する。引き当てはヘルパーに閉じ込め、後から `Map` に差し替えられるようにする。

### 7.5 イベントは Phase 1 では消費者がいない

`DomainEvent` は Phase 2 の永続化・配信・通知の入力になる。Phase 1 では発行するだけで、誰も読まない。それでも設計しておく。後から足すと、状態変化とイベントの対応に漏れが出る。

イベントは「起きたこと」を過去形で表す（`TicketCalled`、`TableFreed`）。コマンド（命令形）と混ぜない。

### 7.6 タイムゾーンは core に持ち込まない

core は UTC のミリ秒だけを扱う。運用時間帯の判定（7.14）に必要な「施設のローカル時刻」は、境界側で変換して core に渡す。core に `Intl` やタイムゾーンデータベースを持ち込まない（依存ゼロを守る）。
