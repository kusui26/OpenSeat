# 0017. 画面の部品一式（shadcn/ui）は入れず、素の要素で作る

- **状態**: Accepted
- **日付**: 2026-09-22
- **関連**: 開発プラン 9.3・10.4、[Phase 2 のプラン](../260921_plan_Phase2.md) PR 6、[ADR-0016](0016-serving-the-app.md)

## 背景

Phase 2 のプランは PR 6 の足場を「React + Vite、React Router、**Tailwind + shadcn/ui**、TanStack Query」と書いていた（9.3）。実装してみると、**利用者の 3 画面に要る部品は 2 つしかなかった。**

| 部品 | どこで使うか |
|---|---|
| ボタン | 受付の登録、チケットの各操作、人数の増減 |
| 人数のステッパー | 受付と、人数の変更 |

ほかはすべて、見出し・段落・箇条書き・リンクである。

## 選択肢

| 案 | 利点 | 欠点 |
|---|---|---|
| A. プランどおり shadcn/ui を入れる | 画面が増えたときに部品が揃っている。見た目が揃う | **ボタン 2 つのために依存が 4 つ増える**（Radix・cva・clsx・tailwind-merge）。支援技術の挙動を自分で確かめ直すことになる |
| **B. 素の要素で作り、増えたら考える** | `<button>`・`<output>`・`<ul>` は**支援技術がいちばんよく知っている形**である。依存が増えない | 画面が増えたとき、部品を自分で揃えることになる |
| C. 別の一式（Radix 単体、Headless UI など）を入れる | A より軽い | 結局同じ判断を先送りするだけ |

## 決定

**B を採る。** プランの「Tailwind + shadcn/ui」は「Tailwind」に直す。

**PR 13・14（スタッフ・管理の画面）で改めて判断する。** あちらには表・ダイアログ・トースト・ドラッグでの席配置が出てくるので、そのときには一式が要るかもしれない。

## 理由

- **利用者の画面でいちばん大事なのは、読めることと押せることである**（10.4）。立ったまま、片手で、屋内の明るいところで見る。`<button>` に大きさと名前を与えれば足り、**素の要素のほうが読み上げも拡大も確実に効く。**
- **`<output aria-live>` のような、意味そのものを持つ要素が使える。** 部品一式は `<div role="...">` に寄せがちで、同じことをするのに宣言が増える。
- **依存は運用の負債である**（14.4）。施設や地域の IT 事業者がこれを引き取る。**更新の必要な依存は少ないほうがよい。**
- **いま入れなくても、あとから入れられる。** 逆は難しい。shadcn/ui はコードを自分のリポジトリに書き出す方式なので、**あとから入れても既存の部品と共存できる。**

## 影響

- `apps/web/src/components/` に、素の要素を包んだ部品を置く（`button.tsx`、`stepper.tsx`、`layout.tsx`、`state-line.tsx`、`countdown.tsx`）。**見た目の決まりごとはここに集める**
- **同じものを 2 つ書かない。** 受付と人数の変更が同じステッパーを使う（片方だけ直すと操作感が食い違う）
- 画面の部品（`.tsx`）の行数の上限を 40 行にした（CLAUDE.md 4 章）。**20 行は論理の量を測る目安**で、JSX は論理ではなく組み立てだからである。数を合わせるために部品を割ると、props の型注釈が増えて**かえって読みにくくなる**ことを実測した
- **見直すきっかけ**: PR 13・14 で、表・ダイアログ・トーストが要ったとき。あるいは自前の部品が 10 を超えたとき（そこまで来たら、揃った一式のほうが安い）
