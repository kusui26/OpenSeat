# 0014. 権限は `core` の表で決め、`apply` を公開しない

- **状態**: Accepted
- **日付**: 2026-09-22
- **関連**: CLAUDE.md 3.2(4)・3 章、開発プラン 9.8、[ADR-0004](0004-pure-domain-core.md)、[ADR-0011](0011-who-may-free-an-uncertain-seat.md)、[Phase 2 のプラン](../260921_plan_Phase2.md) PR 3

## 背景

誰がどのコマンドを出せるかを決めなければならない。役割は owner / admin / staff と、利用者側の匿名・本人である（9.8）。

CLAUDE.md 3.2(4) は**表として宣言し、`dispatch` が適用の前に必ず評価する**ことを求めている。求めていないのは「どこに置くか」と「どうやって迂回できなくするか」である。

**迂回できるかどうかが本題である。** CLAUDE.md 3 章の判定基準は 1 つだけだった。

> **コントローラーとビューを何度書き換えても、データの整合性が壊れないこと。**

権限も同じである。**ハンドラを何度書き換えても、権限が変わらないこと。** 「境界が評価する約束」では、次に書かれるハンドラがその約束を知らない。

## 選択肢

| 案 | 内容 | 利点 | 欠点 |
|---|---|---|---|
| A | 表は `core`、評価は**境界**（サーバの施設アクター） | `core` の入口が変わらない | **迂回できる。** `apply` を直接呼ぶ道が残り、検査を足しても「呼ばないこと」の確認にしかならない |
| B | `apply` に実行者を足す（`apply(state, actor, command, now)`） | 迂回できない | **呼び出し 177 か所に実行者を書くことになる。** その大半は状態機械のテストで、権限とは関係が無い |
| **C** | **`dispatch` を足し、`apply` を公開しない** | 迂回できない。既存の呼び出しは変わらない | `core` の中からは `apply` を呼べる（テストがそうしている） |

## 決定

**C を採る。`dispatch(state, actor, command, now)` を足し、`apply` をパッケージの外に公開しない。**

- 権限表は [`packages/core/src/domain/permissions.ts`](../../packages/core/src/domain/permissions.ts)。**役割 × コマンドの全 22 行**を `satisfies Record<CommandType, readonly Role[]>` で宣言する
- 実行者は [`packages/core/src/domain/actor.ts`](../../packages/core/src/domain/actor.ts)。**役割（誰か）と、記録に残る側（利用者側かスタッフ側か）を分ける**
- `dispatch` は 3 つを見てから `apply` へ渡す。**権限 → 本人性 → 名乗りの一致**

## 理由

- **迂回できないことに価値がある。** B と C は同じ保証を与えるが、C は既存の 177 か所を触らずに済む。触らずに済むぶん、**この PR で壊れる可能性のある場所が減る**。
- **`core` の中から `apply` を呼べることは、欠点として小さい。** 呼んでいるのは状態機械のテストで、そこで確かめたいのは遷移であって権限ではない。**権限には権限のテストがある**（役割 × コマンドの 110 通りの総当たり）。むしろ、状態機械のテスト 1 つ 1 つに実行者を選ばせると、**権限の信号が状態機械の雑音に埋もれる**。
- **役割と「側」を分けたのは、必要な細かさが違うからである。** 「管理者が取り消した」と「スタッフが取り消した」は統計では同じ（どちらも `staff_cancel`。7.9）だが、権限では違う。逆に「匿名」と「本人」は権限では大きく違うが、記録ではどちらも利用者側である。1 つの型に押し込むと、`Record<Role, EndReason>` に**到達しない行**（匿名の取り消し）が並ぶ。
- **本人性を `core` が見るのは、そこがドメインの条件だからである。** 「チケット A の秘密パラメータでチケット B を取り消せない」は、**どのチケットを相手にしているか**という関係の条件で、境界が確かめた身元とは別物である。境界に任せると、次に書かれるハンドラがその確認を忘れる。
- **「全席解放」は現場のスタッフが押せる。** CLAUDE.md 3.2(4) の例は `['admin', 'owner']` と書いていたが、実装では `['staff', 'admin', 'owner']` にした。**障害時に自由席へ戻す手順（12.6）が最優先**で、CLAUDE.md 8 も「全席解放の動作は常に保てるように」と求めている。実証実験の現場は開発者を含めて 2〜3 名（12.2）で、管理者が居ない時間帯に**復旧の道が塞がる**ほうが重い。2026-09-22 に開発者が判断し、CLAUDE.md の例を実装に合わせた。
- **A を採らなかったのは、検査で守れないからである。** 「ルートで役割を判定しない」は検査できる（足した）が、「`apply` を呼ぶ前に必ず権限を見る」は検査しにくい。**見えないものを約束にしない。**

## 結果

- **`core` が公開する入口は `dispatch` と `tick` の 2 つになった。** これまでの `apply` は公開しない
- **シミュレータも `dispatch` を通る。** 100 回 × 3 時間半のファズが、権限表も一緒に踏む。許していない組み合わせを出せば「想定外の拒否」として出る
- 拒否コードが 2 つ増えた。`FORBIDDEN`（役割が足りない／他人のチケット）と `ACTOR_MISMATCH`（コマンドの名乗りと実行者の食い違い）。後者は**欠陥**として扱う —— 入力の誤りではなく、境界の組み立ての誤りだからである
- `Actor`（利用者側かスタッフ側かの 2 値）は `Side` に改名した。**値は変わっていない**ので、`by: 'staff'` と書いてある 200 か所以上はそのままである
- 「ルートで役割を判定していない」を `pnpm check:arch` に足した。CI の自己点検にも入れてある
- **見直すきっかけ**: 役割ごとの権限が施設ごとに変わるようになったとき（表が設定になる）。あるいは、`core` の中から `apply` を呼ぶ道が実際に事故を起こしたとき（そのときは B へ移る）
