# 0013. 状態は行そのものとして持ち、イベントは配信と統計と監査のために別に残す

- **状態**: Accepted
- **日付**: 2026-09-22
- **関連**: 開発プラン 9.4・9.6・9.12、[ADR-0004](0004-pure-domain-core.md)、[Phase 1 のプラン](../260917_plan_Phase1.md) PR 14、[Phase 2 のプラン](../260921_plan_Phase2.md) PR 1

## 背景

落ちても状態を取り戻せなければ、実証実験は成り立たない。何をどう記録するかを決める。

**開発プラン 9.4 は、こう書いている。**

> 発生したイベントは同一トランザクションで SQLite に追記し、状態スナップショットを更新してから WebSocket に配信する。**起動時はスナップショット＋以降のイベントで復元。**

**この「以降のイベントで復元」は成り立たない。** Phase 1 の PR 14（指標の収集）で分かった。

> **イベントログだけでは、席の稼働率を計算できない。** `TableReportedInUse` は「使用中（誰か不明）」と「使用中（本人）」の両方へ向かい、`StillHereAnswered` は席が確認要から使用中へ戻ったことを語らず、`VenueOpened` はどの席が運用に戻ったかを持たない。**イベントは「起きたこと」を語るが、「席がいまどの姿か」を語る責任を負っていない。**

稼働率が出せないのと、状態が組み直せないのは、同じ 1 つの事実の裏表である。**スナップショットが遅れた瞬間に、その遅れを埋める手段が無くなる。**

イベントの契約を「状態を復元できるだけの情報」に作り変える道もあるが、それは `core` のイベントを**消費者のためでなく復元のために**設計し直すことで、Phase 1 で決めた形（起きたことを語る）を捨てることになる。

## 選択肢

| 案 | 内容 | 利点 | 欠点 |
|---|---|---|---|
| A | **イベントが唯一の真実**。状態は毎回組み直す | 記録が 1 本。監査と状態が必ず一致する | **いまのイベントでは組み直せない。** 契約を作り直すと `core` の設計が変わる |
| B | **スナップショット 1 行**（`VenueState` を JSON で）＋イベント | 往復が単純。9.4 の記述に近い | **整合性を DB の制約として書けない**（塊に一意インデックスは張れない）。9.6 の表と二重持ちになる |
| **C** | **行そのものが状態**（`venues` ＋ `tables` ＋ `tickets`）＋イベント＋席の姿の履歴 | 制約が効く。9.6 とそのまま一致。管理画面が素直に読める | 書き込みに順序の配慮が要る。往復の一致をテストで守る必要がある |

## 決定

**C を採る。記録は 3 本立てにする。**

| 記録 | 何のため | 書くとき |
|---|---|---|
| **`venues` ＋ `tables` ＋ `tickets` の行** | **復元のため。これが状態そのもの** | 状態が変わるたび、同じトランザクションで |
| **`events`** | 配信（9.5）・統計（8.3）・監査（CLAUDE.md 7）のため | 同じトランザクション |
| **`table_status_log`** | **稼働率のため**（8.3）。席がどの姿に、いつからいつまでいたか | 同じトランザクション。姿が変わった席の分だけ |

**別にスナップショットの塊は持たない。** 行がスナップショットそのものである。

## 理由

- **遅れを作らないほうが、遅れを埋める仕掛けより強い。** 9.4 が「スナップショット＋以降のイベント」と書いたのは、スナップショットの更新が遅れることを前提にしていたからである。毎回同じトランザクションで行を書けば、埋める対象がそもそも生まれない。1 分に数十件（9.1）の更新は SQLite には軽い。
- **整合性を DB の制約として表せる**（CLAUDE.md 3.2(1)）。JSON の塊には部分一意インデックスを張れない。**1 つの席に有効なチケットは最大 1 枚**（`one_ticket_per_table`）を DB でも縛れるのは、行で持つからである。`core` の不変条件のうち 1 つの表の中で言えるものは、すべて `CHECK` として書いた（`db/schema.ts`）。
- **二重に持たない**（CLAUDE.md 4 章）。9.6 のデータモデルは、すでに `tables` と `tickets` を宣言している。塊を足すと同じものが 2 か所に載り、**どちらが正かという問いが生まれる**。制約が塊の写しにしか効かないなら、それは飾りである。
- **読む側が素直に書ける。** スタッフコンソール（PR 14）と管理画面（PR 13）、Phase 3 のレポートは、行を読めば済む。
- **A を採らなかったのは、イベントの契約を復元のために曲げたくないからである。** Phase 1 のイベントは消費者（通知・ボード・統計）のために設計されている。復元の都合を足すと、消費者に要らない情報が混ざり、終わり方を足すたびに消費者側の分岐が増える。

## 結果

**開発プラン 9.4 を直した。** 「起動時はスナップショット＋以降のイベントで復元」は誤りなので、「起動時は行から組み立てる」に改めた。9.6 のデータモデルにも、足りていなかった列と表を足した。

**席の姿の履歴は投影である。新しい真実ではない。** 書くのは境界側（`db/repository.ts`）で、変更の前後の状態を両方知っているから差分だけで済む。**`core` のイベント契約には触っていない。** 形はシミュレータの `TableSpan` と同じなので、Phase 1 の `sim/metrics.ts` がそのまま使える。

**順序を問うときは `seq` を見る。`at` ではない。**

`core` は期限で起きたことを**期限の時刻**で記録する（`settle.ts`・`tick.ts`）。`tick` が 3 分遅れて走っても「3 分前に呼び出しが切れた」と残るので、統計が走らせ方に左右されない。そのかわり、**先に記録したイベントより前の時刻を持つイベントがある。** 配信の追いつき（9.5）でここを取り違えると、静かに取りこぼす。あわせて `recorded_at`（こちらに記録した時刻）も持つことにした。**`at` との差が、そのまま `tick` の遅れになる**（CLAUDE.md 8 の監視）。

**行は書いた順に読み戻す。** `core` の `VenueState` は席とチケットを配列で持つ。ID 順で返すと `k-9` と `k-10` の前後が入れ替わり、**再起動する前と後で並びが変わる**。SQLite の `rowid` で並べて、書いた順そのものを返す。

**書き込みには順序がある。** 部分一意インデックスも `CHECK` も、文が 1 つ終わるたびに判定される。「A が席を離れ、B がその席に着く」を 1 回の適用で記録するとき、B を先に書くと一瞬だけ 2 枚になって**正しい変更のほうが弾かれる**。片付け猶予が 0 分（既定）なら毎回起きる。途中に嘘の行を置いて逃げることもできない（`CALLED` のまま席を持たない行は `assigned_has_table` が落とす）。**席を手放すチケットから順に書く**ことで解いた（`db/repository.ts`）。

**申し送り: 席の `status_since` が前に戻ることがある。**

呼び出しの期限が切れたあと `tick` が走る前に、本人が別の空席の QR を読んで席を変えると、**あとで確保した席が、それより前の時刻に空く**。`tick` は 10 秒ごとに走るので窓は狭いが、落ちていたあいだは広がる。`status_since` は片付け猶予も無断利用の期限も測る起点なので、戻ると期限の計算が狂う。**いまは記録側で丸めてある**（区間の境目が前に戻らないようにする）が、根は `core` にある。施設アクターと `tick` を作る PR 3 で片づける。丸めを外せるようになったら、`db/roundtrip.test.ts` の固定テストが落ちて知らせる。

**見直すきっかけ**: 行の書き込みが重くなったとき（席 100・チケット 1,000 を超える規模）。そのときは差分の取り方を見直す。あるいは、施設をまたいだ集計が要るようになったとき（Phase 3 のレポートが `table_status_log` で足りなくなったとき）。
