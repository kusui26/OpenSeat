# 0019. 試行は Railway に置き、実証実験の前に国内 VPS へ移す。複製先は Cloudflare R2 とする

- **状態**: Accepted
- **日付**: 2026-09-25
- **関連**: 開発プラン 9.11・9.13・14.2、[ADR-0005](0005-single-container-sqlite.md)、[ADR-0006](0006-who-pays-for-hosting.md)、[ADR-0018](0018-server-sent-events.md)、[Phase 2 のプラン](../260921_plan_Phase2.md) PR 9

## 背景

[ADR-0005](0005-single-container-sqlite.md) は成果物を「1 つのコンテナと SQLite」と決め、**試行段階の置き場を Railway、引き渡し先の既定を国内 VPS** とした。PR 9 でそれを実行するにあたり、前提が変わっていないかを調べ直した。

**3 つを切り分けて考える。** 混ざりやすいが、別のものである。

| | 何を決めるか | 誰に見えるか |
|---|---|---|
| 成果物 | 施設に渡すもの | 施設 |
| **試行の置き場** | 開発者が実証実験のために置く場所 | **誰にも見えない** |
| 施設の導入ハードル | 施設が引き取るときの障壁 | 施設 |

**試行の置き場は、施設の導入ハードルを変えない。** 施設に渡るのは同じ 1 つのイメージで、開発者がどこへ置いたかは施設の手元に現れない。

## 調べて分かったこと（2026-09-25 時点）

| | Railway | Fly.io 東京 | 国内 VPS |
|---|---|---|---|
| 月額 | **$5〜7 ≒ 800〜1,110 円** | $7.2 ≒ 1,140 円（512MB） | 600〜900 円 |
| 日本リージョン | **無い**（最寄りシンガポール） | ある | ある |
| 長い HTTP 接続 | **15 分で切られる** | 上限の記載なし | 自分で決められる |
| ボリューム | Hobby は 5GB まで | 500GB まで | ディスク次第 |
| 手間 | ほぼゼロ | ほぼゼロ | 初回 3〜5h ＋ 月 30 分 |

**想定していなかったのは 2 つ。** Railway に日本リージョンが無いこと（4 リージョンのみ）と、**HTTP リクエストが 15 分で切られる**ことである。後者は公式ドキュメントに明記されている。

> HTTP requests can run for up to 15 minutes if data keeps transferring … Websocket connections are exempt from these duration and inactivity limits.

Fly.io の東京は**リージョン倍率 2.0**（東京・シンガポール・シドニーは基本価格が 2 倍）で、月 1,000 円の枠を超える。

## 決定

**試行は Railway に置く。実証実験の前に国内 VPS へ移す。複製先は Cloudflare R2 とする。**

## 理由

- **15 分の上限は、配信の設計が既に吸収している。** [ADR-0018](0018-server-sent-events.md) で「つなぐたびに現在の姿を送る」形にしたため、強制切断は**約 1 秒の遅れ**にしかならない。位置から差分を再生する設計にしていたら、ここで取りこぼしの処理が要った。ping は 20 秒ごとなので「5 分無通信で切断」にも当たらない。
- **倍率 2.0 を払って買えるのは 60〜80ms の短縮だけである。** 要件は「呼び出しから画面の更新まで数秒以内」（9.1）で、桁が 2 つ違う。予算（14.2 の月 1,000 円）を超えてまで買うものではない。
- **置き場は半日で移せる。** ドメインを固定しておけば、移行は施設にも利用者にも見えない。**後戻りできないのはドメインのほうである** —— 卓上 POP に刷った QR は刷り直すしかない。
- **実証実験の前に VPS へ移すのは、それが引き渡しの予行になるからである。** ADR-0005 が引き渡し先の既定を国内 VPS としており、試行をそこで回しておけば、手順書が机上のものでなくなる。費用も下がり、レイテンシも 15 分の上限も消える。
- **複製先は、鍵の及ぶ範囲で決めた。** Supabase Storage（すでに契約済みで費用 0 円）を第一候補としていたが、**S3 アクセスキーが「プロジェクト内の全バケットにフルアクセスし、RLS を迂回する」**と公式に明記されており、バケット単位に絞る手段が無い。**バックアップの鍵が、無関係な本番データに届いてはならない。** R2 の API トークンはバケット 1 つに絞れる。
- **R2 の無料枠は、この用途なら届かない。** 当初 R2 を避けたのは「Litestream が毎秒書くと月 260 万回に達し、無料枠 100 万回を超える」という見立てだったが、**それは 24 時間書き続けた場合の数字**で、実証実験（土日 4 日間、運用は 1 日 8 時間）では月 30 万回程度にとどまる。足りなくなったら `sync-interval` を伸ばせばよい（5 秒にすれば 5 分の 1）。
- **Firebase / GCS も検討したが、採らなかった。** 書き込みが $0.005/1,000 回の従量（無料枠は月 5,000 回、しかも米国 3 リージョンのみ）で、転送も有料。さらに Litestream の GCS は**鍵が JSON ファイル**なので、環境変数に文字列 2 つを置くだけでは済まない。

## 影響

- **Litestream をイメージに同梱した。** 版は 0.5.17 に固定する —— **0.5 系は 0.3 系の複製から戻せない**（形式が変わった）ので、勝手に上げ下げすると手元の複製が使えなくなる
- **複製は任意にした。** `LITESTREAM_REPLICA_URL` が空なら複製せずに起動する。**S3 を持たない施設でも `docker compose up -d` が通ること**（11.4）を守るため。宛先には同じホストの別ディスク（`file://`）も選べる
- **起動時に、記録が無ければ複製から戻す。** 新しいホストで起こしたときに効く
- **`SIGTERM` は届く。** `entrypoint.sh` が `exec` で自分を置き換え、Litestream が受け取った合図を子へ渡す（手元で確認済み）
- **再接続に散らし（full jitter）を入れた。** 15 分の上限があると、開店直後につないだ数百台が**揃って切れ、揃って戻る。** 散らさないとそれが一日続く
- `infra/restore-drill.sh` で**復元を繰り返し確かめられる**ようにした。バックアップは「取れていること」ではなく「戻せること」で測る
- **見直すきっかけ**: 実証実験の準備期間に入ったとき（VPS へ移す）。あるいは Railway の 15 分上限が設計に合わなくなったとき（配信を WebSocket に替えるか、置き場を替えるか）
