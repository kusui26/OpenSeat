# 0004. ドメインロジックを依存ゼロの純粋関数として `packages/core` に置く

- **状態**: Accepted
- **日付**: 2026-09-16
- **関連**: 開発プラン 9.4、9.12、8 章、`.claude/CLAUDE.md` 第 3 章

## 背景

多くのソフトウェアは、データを扱うモデル、UI を提供するビュー、その間を繋ぐコントローラーから構成される。未熟な実装では、データの整合性やビジネスロジックの責任をコントローラーに押し込んだ結果、**ファット・コントローラー**と呼ばれる保守困難な構造になる。生成 AI に書かせる場合、AI は「何が大切か」という価値観を持たないため、指示がなければこの構造を作る。

OpenSeat には「1 つの席に 2 組を割り当てない」という、破られたら製品が成立しない不変条件がある。加えて、実証実験の前にシミュレーション（開発プラン 8 章）で割当方針を比較する必要があり、サーバとシミュレータで同じロジックが動くことが要件になる。

## 選択肢

| 案 | 内容 | 問題 |
|---|---|---|
| ロジックをハンドラに書く | 素直で速い | ファット・コントローラーになる。シミュレータで再利用できない。機能追加のたびに整合性が壊れる |
| ロジックを DB の関数に書く | DB の制約と近い | シミュレータで動かせない。テストが重い。実装が SQL に閉じる |
| **純粋関数として独立させる** | `(state, command, now) → { state, events }` | 状態の読み書きを呼び出し側が担うため、境界の設計が要る |

## 決定

**ドメインロジックを `packages/core` に純粋関数として置き、依存ゼロを維持する。** 併せて、モデル層を宣言的に定義して機械的に検証する。

- スキーマは Drizzle の定義を唯一の出典とし、整合性は可能な限り DB の制約として表現する
- 状態遷移は**遷移表**として宣言し、表にない遷移は失敗させる
- 不変条件は**名前付きの述語**として宣言し、全コマンド適用後に検査する
- 権限は**表**として宣言し、`dispatch` が適用前に評価する
- API 契約は Zod を唯一の出典とし、型は `z.infer` で導出する

## 理由

- 「気をつける」では守れない。**構造的に不可能にする**必要がある。
- 純粋関数であれば、サーバ・シミュレータ・テストの 3 か所で同じコードが動く。ロジックを二重に実装しない。
- 不変条件を述語として 1 か所に宣言すれば、同じものを実行時検査・性質テスト・シミュレーションのファズの判定に使える。
- 判定基準を 1 つに定められる。**コントローラーとビューを何度書き換えても、データの整合性が壊れないこと。**

## 結果

- `packages/core` では `Date.now()`、`Math.random()`、`process.env`、I/O を使えない。時刻は必ず引数で受け取る。これを lint で強制する。
- `apps/server/routes/**` から `db/` を直接 import することを禁止し、依存方向を CI で検査する。この検査を通らない実装は、動いていてもマージしない。
- コントローラーが書いてよいのは、入力の検証・実行者の特定・コマンドの組み立て・モデルへの委譲・結果の整形の 5 つだけになる。
- 状態を毎回読み書きする分のコストが増えるが、1 施設あたり席 20〜100・更新は 1 分に数十件という規模では問題にならない。
