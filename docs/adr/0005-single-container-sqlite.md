# 0005. 単一コンテナと SQLite を採用し、Vercel + Supabase を採らない

- **状態**: Accepted
- **日付**: 2026-09-16
- **関連**: 開発プラン 9.3、9.13、14.4、ADR-0006

## 背景

開発者は普段 Vercel と Supabase（ともに Pro プラン）で開発しており、両方の追加費用はほぼ発生しない。一方で、継続段階の運用費を開発者が持ち続けることはできない（ADR-0006）。したがって**運用を他者が引き取れること**が必須要件になる。

この選定は一度見直している。当初は自前ホスト要件から単一コンテナを選び、Pro プラン契約済みという事実を受けて Vercel + Supabase に傾き、運用費の制約を受けて再び単一コンテナに戻した。

## 選択肢

| 案 | 技術的な成立性 | 引き渡し |
|---|---|---|
| **Node + Hono + SQLite（単一コンテナ）** | 施設単位の直列化がプロセス内で自然。`tick` は `setInterval` | **1 サービス、メモリ 512MB〜1GB** |
| Vercel + Supabase | **成立する。** 直列化は `pg_advisory_xact_lock`、時刻起因の遷移は Supabase Cron（1 秒間隔から設定可）、Pro は非アクティブでも停止しない | **13 サービス、本番推奨でメモリ 8GB 以上・4 コア以上・SSD 80GB 以上** |

## 決定

**単一コンテナと SQLite を採用する。** 試行段階の置き場は Railway、引き渡し先の既定は国内 VPS とする。

## 理由

- **不採用の理由は技術ではなく引き渡しにある。** Vercel + Supabase は技術的に成立する。Vercel Cron は Pro でも最短 1 分だが、Supabase Cron は 1 秒間隔から設定でき、10 秒ごとの `tick` は問題なく回せる。
- 自前ホストの Supabase は 13 サービスで、本番推奨がメモリ 8GB 以上・4 コア以上である。単一コンテナは 1 サービスで 512MB から動く。**約 10 倍の差**があり、「引き取ってください」と言えるのは前者だけである。
- 日本企業にとって米ドル建ての海外 SaaS は調達の障壁になる（法人カード、為替処理、登録番号のない英文請求書）。国内 VPS は円建て・請求書払いで調達できる。
- 引き渡しが前提なら、移植可能な成果物を最初から作るほうが総工数が少ない。Supabase で作って後から移すと、データ層と配信層を 2 回書くことになる。
- SQLite の公式ドキュメントは「1 日 10 万ヒット未満のサイトなら問題なく動く」としている。本計画の想定は 1 施設あたり同時接続 100〜300、更新は 1 分に数十件で、桁が 2 つ以上違う。「書き込みは常に 1 つだけ」という制約も、割当を施設単位で直列化する設計と一致する。

## 結果

- Hono・SQLite・Docker は開発者にとって未経験のため、**Phase 2 の冒頭に 1 日のスパイク**を置く。Hono と SQLite で最小のアプリを書き、Dockerfile を作り、Railway に置いて独自ドメインで開くところまでを 1 日で通す。通らなければこの決定を見直す。
- Phase 1 は純粋な TypeScript のみを書くため、この判断の実行は Phase 2 まで先送りできる。
- プラットフォームの再販禁止条項（Vercel 第 11 条、Supabase 第 2(c)）は Railway にも同種の文言があり、選定の理由にはならない。守るべき原則は「**施設ごとにプラットフォームのアカウントやプロジェクトを作らず、自分が所有する 1 つのマルチテナントなアプリを運用すること**」である。
- Cloudflare Workers + Durable Objects への移植は、`packages/core` が純粋である限り v2 の選択肢として残る。
