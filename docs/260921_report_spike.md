## 2. 確かめたこと

### 2.1 `packages/core` は、サーバから素直に呼べる

`apps/spike` はワークスペース依存（`workspace:*`）で `@openseat/core` を使い、`apply` と `tick` をそのまま呼んでいます。**ESM（NodeNext）のまま、変換も回避策も要りませんでした。**

受付から退席までを実際に通しました。

```
受付 2 名 → A-1（2 名席）に割当・呼び出し   ← ロス最小が効いている（7.6）
受付 4 名 → B-1（4 名席）に割当・呼び出し
着席 → A-1 = OCCUPIED
退席 → A-1 = FREE
```

**拒否も `core` の言葉でそのまま返りました。**

```
POST /tickets/{終わったチケット}/check-out
→ 409 NOT_ALLOWED_IN_STATE: DONE のチケットに CHECK_OUT は起こせない
```

境界が言い換えていません。利用者向けの文言は `packages/shared` の i18n に置くのが 4 章の決まりですが、**その仕組みは Phase 2 で作ります**（ここで作ると二重に持つことになる）。

**層の分け方も、小さいまま守れました。** ハンドラは「入力の検証 → コマンドの組み立て → モデルへ委譲 → 整形」の 4〜5 行で、業務の判断はすべて `core` にあります（CLAUDE.md 3.1）。**スパイクの規模でも窮屈ではなかった**ことは、Phase 2 への良い知らせです。

### 2.2 `node:sqlite` は使えるが、実験的である

**旗（`--experimental-sqlite`）なしで動きます。** 9.13 の「Node.js 22 以降は `node:sqlite` が標準で入っている」は正しい。ただし、

```
(node:30839) ExperimentalWarning: SQLite is an experimental feature and might change at any time
```

が毎回出ます。**「いつ変わってもおかしくない」と公式が言っている機能**の上に、実証実験の記録を置くことになります。

> **Phase 2 で決めること。** 9.3 は ORM に Drizzle を採ると決めています。Drizzle の SQLite ドライバは `better-sqlite3` / `libsql` / `node:sqlite` から選べるので、**スキーマを書き始める前にどれにするか決めてください。** `better-sqlite3` はネイティブ拡張なので、Alpine で組み立てるならビルド道具が要ります（イメージが大きくなります）。`node:sqlite` は依存ゼロですが実験的です。**この選択は Dockerfile の複雑さに直結します。**

### 2.3 落ちても、まったく同じ状態に戻る

**これがいちばん大事な確認でした。**

記録しているのは **`core` に入れたもの（コマンドと、状態が動いた `tick` の時刻）だけ**です。起動時にそれを順に流し直します。`apply` と `tick` は純粋関数なので、同じ入力からは必ず同じ状態が出ます（[ADR-0004](adr/0004-pure-domain-core.md)）。

実際に落として起こし直し、**時刻を除いて状態が完全に一致する**ことを確かめました。

```
停止前  席: A-1=FREE B-1=HELD / チケット 2 件 / nextCodeSeq 2
再起動後 席: A-1=FREE B-1=HELD / チケット 2 件 / nextCodeSeq 2
→ 一致（時刻を除いて同じ状態に戻った）
```

**新しい形式を 1 つも決めずに、取り戻しを確かめられた**のが要点です。本番はイベントログ＋スナップショットになります（9.2）が、**その形式を決めるのは Phase 2 です。**

なお、何も起きなかった刻みは記録しません（`tick` は冪等なので流し直す必要が無い）。記録は 1 回の受付〜退席で 5 件ほどに収まりました。

### 2.4 10 秒ごとの `tick` が回る

`clockAt` が 10,002 ミリ秒進むことを確かめました（9.4 の 10 秒間隔）。**個別のタイマーを持たない設計**（CLAUDE.md 3.4）が、そのまま動いています。

### 2.5 長い接続（SSE）が保つ

画面を勝手に更新するために、SSE を 1 本だけ置きました。**依存は増やしていません**（Hono に入っています）。

```
event: ping        ← 接続直後
data: changed      ← ほかの人が受付した
event: ping        ← 15 秒後
```

**これは 9.2 の WebSocket と同じ risk を、安く見るために置いたものです。** 9.13 の文面には無い追加ですが、Phase 2 の配信方式を決める前に「長い接続が置き場のプロキシ越しに保つか」を知りたいので入れました。**手元では保ちます。Railway 越しはまだ確かめていません。**

### 2.6 取り出した一式だけで動く

`pnpm --filter ./apps/spike --prod deploy --legacy` が **4.3 MB** の自己完結した一式を作り、**それ単体で動きました**（`@openseat/core` も入っている）。Dockerfile のいちばん壊れやすい行がここなので、Docker 抜きで先に確かめてあります。

## 3. 確かめられなかったこと

### 3.1 コンテナのイメージを組めていない ⚠️

**`docker build` が、ベースイメージの取得で止まりました。**

```
#3 [internal] load metadata for docker.io/library/node:22-alpine
（以降、出力なし）
```

切り分けた結果はこうです。

| 調べたこと | 結果 |
|---|---|
| Docker のデーモンは生きているか | **生きている**（`docker ps` は即座に応答する） |
| Docker Hub に届くか | **届く**（`registry-1.docker.io` が 0.59 秒で 401 を返す＝正常） |
| `docker pull node:22-alpine` | **無応答**（90 秒待っても 1 行も出ない） |
| `docker pull hello-world` | **無応答**（`Using default tag: latest` の次で止まる） |
| ECR のミラー（`public.ecr.aws/docker/library/node`） | **無応答** |
| 認証ヘルパー | `~/.docker/config.json` の `credsStore` が `"desktop"` |

**ネットワークではなく、Docker Desktop 側で取得が止まっています。** どのレジストリからも同じように止まるので、`credsStore: desktop`（Docker Desktop に問い合わせる認証ヘルパー）が応答していない可能性が高い。Docker Desktop は 24.0.5（2023 年の版）で、この確認のために起動したばかりでした。

> **これは Dockerfile の問題である可能性は低いが、手元では確かめられていない。**

組み立ての中身は Docker 抜きで確かめてあります（2.6）ので、**残っている未知は「Alpine の上で同じことが起きるか」だけ**です。ネイティブ拡張を使っていない（`node:sqlite` は Node に入っている）ので、詰まる要素は少ないはずです。

**そこで、CI で組み立てることにしました。** `.github/workflows/ci.yml` に `image` ジョブを足し、**イメージを組み立てて、受付から記録の取り戻しまでを通します**（[`infra/smoke.sh`](../infra/smoke.sh)）。

| CI が確かめること | なぜ |
|---|---|
| `docker build` が通る | スパイクの 4 |
| 起動して `/healthz` が応答する | 置き場のヘルスチェックが効くか |
| 受付した組に席が割り当てられる | `packages/core` がコンテナの中でも動くか |
| 範囲の外の人数を断る | 入力を受け流さないか |
| **コンテナを作り直しても記録が残る** | ボリュームが効いているか。**Railway の再デプロイで記録が消えないか**と同じ形の確認 |

**このジョブが緑なら、スパイクの 4 は閉じます。** 開発者の手元でも、Docker Desktop が直ったら次の 1 行で同じことを確かめられます。

```bash
docker compose -f infra/docker-compose.yml up --build
```

### 3.2 Railway に置いていない ⏸

**人の手が要ります。** アカウントの作成と支払い、ドメインの取得は開発者本人が行うものです。手順は [`infra/README.md`](../infra/README.md) に書きました。

置いたあとに **測るべき数字が 4 つ**あります。どれもスパイクの目的に直結します。

| 測るもの | なぜ |
|---|---|
| **再デプロイの停止時間** | 9.13 が「ボリューム使用時は短い停止が入る」と書いている。何秒かを知らないと、運用時間帯を避ける判断ができない（CLAUDE.md 8） |
| **月額** | 14.2 の「月 1,000 円以内」に収まるか。**9.1 は「月 1,500 円以内」と書いていて食い違っている**ので、あわせて直すこと |
| **長い接続が保つか** | 保たないなら、Phase 2 の配信方式（9.2 の WebSocket）を見直す |
| **記録が残るか** | ボリュームが効いているか。再デプロイで消えるなら、マウント先が違う |

### 3.3 Litestream を試していない

継続バックアップ（9.13、CLAUDE.md 8）には S3 互換のバケットと鍵が要るので、スパイクの範囲から外しました。**Phase 2 の宿題です。** イメージにバイナリを 1 つ足すことになるので、3.1 の Dockerfile が通ってから足すのが順序として正しい。
