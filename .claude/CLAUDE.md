## 1. プロジェクトの概要

**OpenSeat** は、フードコートの「席を探す」を「順番を待つ」に置き換える OSS です。入口の **受付 QR** で人数を登録すると仮想の待ち行列に入り、席が空くと人数に合う席が割り当てられて呼び出されます。各席の **座席 QR** で着席と退席を記録します。センサーもカメラも専用端末も使いません。

- **開発体制**: 個人開発（GitHub ユーザー名 `kusui26`）。リポジトリは `kusui26/OpenSeat`。
- **ライセンス**: Apache-2.0。名称は「OpenSeat」で確定（商標・ドメイン調査済み）。
- **当面の目標**: 横浜の商業施設で、対象席 20〜40 席・土日 4 日間の実証実験を行う（2027 年 3〜4 月を想定）。
- **利用者**: アプリ不要・アカウント不要・入力は人数のみ。個人情報は取りません。

## 2. 最重要原則

AI は「何が大切か」を自分では持ちません。だからここに明記します。**判断に迷ったら、この順序で優先してください。**

1. **データの整合性 > 機能追加の速さ。** 1 つの席に 2 組を割り当てない。この不変条件を守れない実装は、どれだけ便利でも採用しません。
2. **モデル層の責務 > 実装の手軽さ。** §3 の鉄則は例外なく適用します。「今回だけコントローラに書く」を認めません。
3. **説明可能性 > 最適化の精度。** 「なぜ後から来た 4 人組が先に案内されたのか」を一文で説明できないルールは採用しません（計画書 7.1）。
4. **現実との食い違いを前提にする。** システムに物理的な強制力はありません。すべての状態に「現実と食い違っている可能性」を織り込み、回復手段を必ず用意します（計画書 7.11）。「システムが正しい」と主張する実装を書かないでください。
5. **利用者に厳しくしない。** 既定値は常に緩い側に倒します。自動で席を取り上げる、順番を失わせる、といった挙動を既定にしないでください。
6. **個人情報を取らない。** 氏名・電話・位置情報・カメラ画像は収集しません。新機能がこれらを要求するなら、設計をやり直します。
7. **施設がいつでも自由席に戻せる。** 障害時・運用終了時に元の状態へ戻せない機能は作りません。

## 3. アーキテクチャの鉄則 — ファット・コントローラーの禁止

**この章が本ファイルで最も重要です。**

多くのソフトウェアは、データを扱う **モデル**、UI を提供する **ビュー**、その間を繋ぐ **コントローラー** から構成されます。未熟な実装では、データの整合性やビジネスロジックの責任をコントローラーに押し込んだ結果、**ファット・コントローラー**と呼ばれる保守困難な構造になります。AI は放っておくとこれを作ります。

**対策は「気をつける」ことではなく、構造的に不可能にすることです。** OpenSeat では、モデル層を宣言的な記述（DSL）で定義し、整合性とアクセス権を機械的に検証できるようにします。

**達成できているかの判定基準は 1 つです。**

> **コントローラーとビューを何度書き換えても、データの整合性が壊れないこと。**

新しいコードを書いたら、この基準で自己点検してください。「このハンドラのこの行を消したら不整合が起きうるか」を考え、答えが「起きうる」なら、その責務はモデル層にあるべきものです。

### 3.1 層の責務と、越えてはならない境界

| 層 | 置き場所 | してよいこと | **禁止** |
|---|---|---|---|
| **モデル（ドメイン）** | `packages/core` | 状態遷移、割当、ETA 計算、不変条件、権限判定 | I/O 一切。DB・HTTP・時刻取得（`Date.now()`）・乱数・環境変数 |
| **モデル（永続化）** | `apps/server/db` | スキーマ定義、読み書き、トランザクション | ビジネスロジック、条件分岐による業務判断 |
| **コントローラー** | `apps/server/routes` | 入力の検証、実行者の特定、コマンドの組み立て、結果の整形 | **業務判断、整合性チェック、DB への直接書き込み** |
| **ビュー** | `apps/web` | 表示、入力、サーバから来た状態の描画 | 業務判断、期限の判定、権限の判定 |

**コントローラーが書いてよいのは、次の 5 行だけと考えてください。**

```ts
// apps/server/routes/tickets.ts
app.post('/api/v/:venue/tickets', async (c) => {
  const input = JoinRequest.parse(await c.req.json());        // 1. Zod で検証
  const actor = await identifyActor(c);                        // 2. 実行者の特定
  const cmd = { type: 'JOIN', partySize: input.partySize, ... };// 3. コマンド組み立て
  const result = await venues.dispatch(c.req.param('venue'), actor, cmd); // 4. モデルへ委譲
  return c.json(toJoinResponse(result));                       // 5. 整形して返す
});
```

**このルートに `if (ticket.state === 'CALLED')` のような業務判断が現れたら、それは設計の誤りです。** モデル側へ移してください。

### 3.2 モデル層を宣言的に定義する（DSL）

「整合性はモデルで担保する」を実効あるものにするため、次の 5 つを **データとして宣言** し、実装から自動的に検証します。手書きの `if` に散らさないでください。

**(1) スキーマ DSL — Drizzle**

テーブル・列・型・リレーション・一意制約・チェック制約は `apps/server/db/schema.ts` の Drizzle 定義が唯一の出典です。マイグレーションは生成物であり、手書きの SQL を正とはしません。整合性は可能な限り **DB の制約として表現** します。アプリ側のチェックは二重防御であって、代替ではありません。

```ts
// 例: 1 つのテーブルに有効なチケットは最大 1 枚（部分一意インデックス）
uniqueIndex('one_active_ticket_per_table')
  .on(tickets.tableId)
  .where(sql`state IN ('CALLED','SEATED')`)
```

**(2) 遷移 DSL — 状態機械を表として宣言する**

チケットとテーブルの状態遷移（計画書 7.3、7.4）を、コードの分岐ではなく**遷移表**として `packages/core/machine.ts` に宣言します。表にない遷移はバグとして落とします。

```ts
export const TICKET_TRANSITIONS = [
  { from: 'WAITING', on: 'CALL',     to: 'CALLED',  guard: 'fitsCapacity' },
  { from: 'CALLED',  on: 'CHECK_IN', to: 'SEATED',  guard: 'isAssignedTable' },
  { from: 'CALLED',  on: 'EXPIRE',   to: 'PAUSED',  guard: 'firstNoShow' },
  // ...
] as const satisfies readonly Transition[];
```

新しい状態や遷移を足すときは、**この表に追記する以外の方法を取らないでください。**

**(3) 不変条件 DSL — 名前付きの述語として宣言する**

計画書 9.12 の不変条件を `packages/core/invariants.ts` に純粋な述語として並べます。

```ts
export const INVARIANTS = [
  inv('one_ticket_per_table',    (s) => /* 1 席に有効チケットは最大 1 枚 */),
  inv('assigned_has_table',      (s) => /* CALLED/SEATED は必ず席を持つ */),
  inv('no_starvation',           (s) => /* 収まる空席があるのに WAITING が残らない */),
  inv('priority_preserved',      (s) => /* 保留を挟んでも受付時刻の順序が保たれる */),
  inv('tick_idempotent',         (s, s2) => /* 同じ時刻の tick は状態を変えない */),
] as const;
```

- **すべてのコマンド適用後に `checkInvariants(next)` を通します。** 開発・テストでは常時、本番では抽出検査。
- 違反したら**その変更を破棄して失敗を返す**。壊れた状態を書き込まないこと。
- 同じ述語を fast-check の性質テストとシミュレーションのファズの判定にも使います。**二重に書かないでください。**

**(4) 権限 DSL — 誰がどのコマンドを出せるかを表にする**

権限判定をハンドラに散らさず、`packages/core/src/domain/permissions.ts` に宣言します（7.16 の運用パラメータが入る `policy.ts` とは別のものなので、ファイルを分けています）。

```ts
export const PERMISSIONS = {
  JOIN:          ['anonymous', 'ticket_owner', 'staff', 'admin', 'owner'],
  CHECK_IN:      ['ticket_owner', 'staff', 'admin', 'owner'],
  CANCEL:        ['ticket_owner', 'staff', 'admin', 'owner'],
  CONFIRM_FREE:  ['anonymous', 'ticket_owner', 'staff', 'admin', 'owner'],
  RELEASE_ALL:   ['staff', 'admin', 'owner'],
  DISABLE_TABLE: ['admin', 'owner'],
  // ...（全 22 コマンドを並べる。実物が出典）
} as const satisfies Record<CommandType, readonly Role[]>;
```

`dispatch` が適用前に必ず評価します。**ルート側で権限を判定しないでください**（`pnpm check:arch` が落とします）。スタッフ・管理者の操作は例外なく監査ログに残します。

**`apply` はパッケージの外に公開しません。** 権限を通らずに状態を変える道を残さないためです（[ADR-0014](../docs/adr/0014-permissions-in-core.md)）。`core` が公開する入口は `dispatch` と `tick` の 2 つです。

**(5) API 契約 DSL — Zod**

リクエストとレスポンスのスキーマは `packages/shared` の Zod 定義が唯一の出典です。型は `z.infer` で導出し、同じ形の型を手書きしないこと。OpenAPI はここから生成します。

### 3.3 境界を機械的に守る

宣言しただけでは守られません。**CI で落とします。**

- `packages/core` は **依存ゼロ**。`package.json` の `dependencies` を空に保ち、Node の組み込みモジュールも import しない。
- `apps/server/routes/**` から `db/` や `drizzle` を直接 import することを禁止（依存方向の検査を CI に入れる）。
- `packages/core` 内で `Date.now()` / `Math.random()` / `process.env` の使用を禁止（lint ルール）。時刻は必ず引数で受け取る。
- `apps/web` から業務判断を行うヘルパーを export しない。画面は状態を描くだけ。

**この検査を通らない実装は、動いていてもマージしません。**

### 3.4 実行モデル

- 施設ごとに 1 つのアクターが状態を保持し、コマンドを **1 件ずつ順に** 適用します。`apply(state, command, now) → { state, events }` と `tick(state, now) → { state, events }` は純粋関数です。
- `tick` は 10 秒ごとに呼ばれ、ホールド期限・リマインド・保留期限・上限超過を、状態のタイムスタンプから計算して適用します。**個別のタイマーを持たないでください。** 再起動で取りこぼさず、シミュレータでも同じ関数で時間を進められることが要件です。
- イベントは同一トランザクションで永続化し、スナップショットを更新してから配信します。
- **時刻はサーバのみを信頼します。** クライアントには絶対時刻の期限と時計差を渡し、カウントダウンは表示だけを担当させます。保存は UTC、表示は施設のタイムゾーン（既定 `Asia/Tokyo`）。
- コマンドには冪等キーを付けます。モバイル回線の再送で二重適用しないこと。

## 4. コーディング規約

**哲学：人間が一目で理解できるコードを書く。** コードは物語のように読め、命名はストーリーを語る。

- **小さく純粋に**：1 関数は**20 行未満**・単一責務。副作用（HTTP・DB・WebSocket・ファイル）は境界に集め、純粋なデータ変換は `packages/core` へ。関数間の依存を減らし**疎結合**に。**画面の部品（`.tsx`）だけは 40 行**とする —— この行数は論理の量を測る目安であり、JSX は論理ではなく組み立てだからである（[ADR-0017](../docs/adr/0017-no-component-library-yet.md)）。**やるべき分割（重複の共通化・props の名前付き `interface` 化・送信処理の hook 化）はやり切ったうえでの幅**であって、業務判断を画面へ移す口実にしない。
- **不変・関数型**：`let` より **`const`**（`var` 禁止）、変数は極力上書きしない。`for` より **map/filter/reduce**、`.then()` より **async/await**。文字列組立は `let +=` でなく **array + push + join**。ドメインの状態は**新しいオブジェクトを返す**（破壊的更新をしない）。
- **型を厳格に**：明示的型を必ず付ける。**`any` 禁止**。**`as` キャスト禁止 → 型ガード**（`(x: unknown): x is T`）。Zod からは **`z.infer`** で導出（重複型を作らない）。状態やコマンドは**判別可能なユニオン**で表し、`switch` は網羅性を `never` で強制する。
- **DRY・定数・単位**：マジックナンバー禁止 → 名前付き定数。運用パラメータ（`hold_min`、`fairness_override_min`、`time_limit_min` 等、計画書 7.16）は **`packages/shared` の 1 か所**に集約し、施設ごとに上書き可能にする。**変数名に単位**を（`hold_min`、`timeout_ms`、`grace_sec`）。
- **堅牢性**：失敗しうる処理に try/catch ＋**文脈付きエラー**（施設 ID・コマンド種別・フェーズ。**チケットの秘密パラメータ・座席トークン・通知先は含めない**）。外部 API 呼び出しは **`AbortSignal.timeout`** 必須。
- **import**：npm パッケージはトップレベル import（条件付き依存のみ動的 import）。正当な理由なく再エクスポートしない。ライブラリ既存ユーティリティを自作より優先。バージョン移行時は対象バージョンの API シグネチャを検証。
- **文言**：利用者に見える文字列はコードに直書きせず `packages/shared` の i18n に置く。既定は日本語と英語。「予約」という語を使わない（保証できないため。計画書 6.5）。

## 5. テストと検証

**品質ゲート：lint / typecheck / unit test を必ず回す。** 通らないものはコミットしません。

- **性質テスト（最重要）**：`packages/core` の不変条件（§3.2(3)）を fast-check の判定に使い、ランダムなコマンド列を流して違反を探します。
- **シミュレーションによるファズ**：計画書 8 章のシミュレータを回し、不変条件違反を検出します。シミュレータとサーバは**同じ `core` を使うこと**。ロジックを二重に実装しないでください。
- **境界値・エッジケース**を厚く：定員を超える人数、待ちが空で空席あり、待ち先頭が保留中、呼び出し中に席が塞がっていた報告、人数の変更、運用中の席設定変更、ホールド期限と tick の同時刻、退席直後の再割当、片付け猶予 0 分、キャンセルと呼び出しの競合、受付終了直前。**計画書 7.6 のエッジケース表を網羅すること。**
- **ゴールデンテスト**：固定シナリオを流して割当結果と ETA の差分を検知します。ロジックを変えたときに、意図した差分かを目で確認します。
- **契約テスト**：`packages/shared` の Zod スキーマとクライアントの呼び出しが一致していること。
- **時刻**：テストでは時計を偽装して期限切れを再現します。`core` が時刻を引数で受け取る設計はこのためでもあります。
- **E2E**（Playwright）：受付 → 呼び出し → 着席 → 退席、座席 QR の全分岐（計画書 7.8 の表）、ボード表示、スタッフ操作。
- **再起動テスト**：スナップショットとイベントから状態を復元できること。

## 6. Git / 変更範囲 / デバッグ（ガードレール）

**Git（ユーザーの明示的許可なしに書き込み系 git を実行しない）**
- 作業前に必ず `git status` / `git branch` で現在地を確認。想定と違えば確認する。
- **`main` に直接 push しない** → フィーチャーブランチを切って **PR**。実装開始前にブランチ作成。
- `git commit` / `push` / `merge` / `rebase` 前に必ず確認を取る。読み取り系（status/diff/log）は自由。
- **`git add .` 禁止**（ファイルは個別に add）。**未追跡ファイルを削除しない**。
- **`push --force` 禁止・`rebase` 禁止**。マージは **merge commit**（`--merge`）で、**squash 禁止**。
- コミットメッセージのプレフィックス：`feat:` / `fix:` / `refactor:` / `docs:` / `chore:` / `test:`。
- 「PR を作って」＝**PR 作成**（マージではない）。作成前にターゲットブランチを確認。
- **`main` へのマージは本番デプロイを意味します。** ドメインロジック（`packages/core`）・スキーマ・運用パラメータの既定値に触れる PR は、**影響範囲と、実証実験中の挙動がどう変わるかを PR 本文に明記**してください。
- スキーマ変更を含む PR には、マイグレーションと**ロールバック手順**を必ず添えます。

**変更範囲**
- **明示的に依頼された変更のみ**行う。機能・ツール・パッケージ・ベンダー・コンテンツを**自律的に追加しない**。必要そうならまず確認。ドキュメント・コミットメッセージは簡潔に。
- 計画書で「v2 以降」「非目標」とされているもの（計画書 4.6、11.7）を先回りして実装しない。

**デバッグ**
- 修正前に**根本原因を診断**。クイックフィックス（値のハードコード・特定ケースの握り潰し）**禁止**。リグレッションは git 履歴 / diff を確認。
- 不変条件の違反を見つけたら、**違反を握り潰さず、再現する性質テストを先に書いてから**直します。

**日付**
- 今日の日付が必要なら**必ず `date` コマンドで取得**する（モデル内部知識に依存しない）。
- サーバは UTC で保存し、施設のタイムゾーン（既定 `Asia/Tokyo`）で表示します。運用スケジュールは施設のローカル時刻で設定します。

## 7. セキュリティ / 機密

- **収集しない**：氏名・電話番号・位置情報・カメラ画像。人数と状態遷移の時刻だけで動く設計を崩さないこと。
- **利用者の識別**：アカウントなし。端末の匿名トークンとチケット URL の秘密パラメータで本人性を扱います。トークンは保存時にハッシュ化します。
- **座席トークン**：推測不能なランダム値。連番や席番号から導出しないこと。再発行は明示操作のみ。
- **スタッフ・管理者**：メールとパスワード（argon2）＋セッション Cookie、招待制。役割は owner / admin / staff。権限の判定は §3.2(4) の表で行い、ハンドラに書かないこと。
- **ログに出さない**：チケットの秘密パラメータ、座席トークン、セッション、Web Push の購読情報、LINE のユーザー ID、メールアドレス。エラーの文脈情報にも含めないこと。
- **秘密情報**：`.env` で扱い、コミットしない。`.env.example` に鍵の名前だけを置きます。ログ・エラー・スクリーンショット・Issue に貼らないこと。
- **通常の対策**：CSRF トークン、レート制限（受付は端末あたり 1 時間に 5 回など）、セキュリティヘッダ、依存の脆弱性監視、SBOM 生成（CycloneDX）。
- **監査ログ**：スタッフ・管理者の全操作を記録し、管理者が閲覧できること。
- **データ保持**：通知先はチケット終了時に削除。イベントログは 90 日で端末トークンを除去して統計のみ残す。施設はいつでも自施設のデータをエクスポート・削除できること。
- **外部送信**：アクセス解析を入れる場合は自前ホストの軽量なものにし、プライバシーポリシーに送信先を明記します（電気通信事業法の外部送信規律）。第三者へ利用者情報を送る実装を勝手に足さないこと。
- **QR の偽装対策**：卓上 POP に正規ドメインを印字し、受付ページ冒頭にもドメインを表示します。

## 8. 運用ガードレール

- **運用時間中にデプロイしない。** Railway はボリューム使用時に再デプロイで短い停止が入ります。施設の運用時間帯（週末の昼など）を避けてください。
- **本番データを直接編集しない。** 調査は読み取りのみ。修正が必要ならコマンド経由か、スタッフ操作として監査ログに残る形で行います。
- **バックアップ**：Litestream で SQLite を外部ストレージへ継続レプリケーション。スキーマ変更の前には必ずスナップショットを取ります。
- **障害時**：掲示を出して自由席へ戻す手順（計画書 12.6）が最優先。システムの復旧を優先して現場を放置しないこと。「全席解放」操作の動作は常に保てるようにします。
- **監視**：外形監視、エラー通知、tick の遅延と接続数を管理画面に出します。
- **実証実験の期間中**は、当日の設定値を記録し、勝手に変更しないこと。変更は A/B の設計に従います（計画書 12.3）。
- **費用**：試行段階のホスティングは月 1,000 円以内に収めます（計画書 14.2）。これを超える構成変更は提案の前に相談してください。
